# AGENTS.md — NetflixScout

## Avvio dei servizi (due terminali, dalla radice del repository)
```bash
./scripts/start_qdrant.sh                                                              # terminale 1: server Qdrant 1.20.0 su 127.0.0.1:6333
source .venv/bin/activate && uvicorn web_api.main:app --host 127.0.0.1 --port 8000     # terminale 2: backend API per il frontend (un solo worker)
```
Qdrant va acceso prima. Lo script cerca il binario in `$QDRANT_BIN`, poi `bin/qdrant` (non versionato), poi nel `PATH`; se manca lo dice e indica dove metterlo
(release ufficiale 1.20.0). Pronto: `curl http://127.0.0.1:6333/collections` elenca `netflix_scout`; il backend risponde `{"status":"ok"}` su `/health`. Per la chat da terminale: `python app.py`.

## 1. Contesto del Progetto

**Scopo**: assistente conversazionale da terminale che consiglia film usando RAG sul catalogo dei film di Wikipedia italiana (41.138 film, `wikipedia_films_it_v3`), un DB SQL locale read-only di MovieLens 32M (voti, classifiche, generi per anno, tag), l'API TMDb (dati aggiornati: cast, uscite, streaming, serie, persone, trending), l'API OMDb (punteggi IMDb, Metascore, Rotten Tomatoes di un titolo identificato) e la YouTube Data API v3 (video su un film identificato: interviste a regista e cast, making-of, dietro le quinte, commenti degli autori). Risponde solo a domande cinematografiche (classificatore anti off-topic e anti jailbreak).

**Stack**
- Python 3.11 (`.venv/` locale), nessun `pyproject.toml`: le dipendenze stanno in `requirements.txt` (versioni pinnate).
- LLM ed embedding: `openai` (Responses API + Chat Completions per il classificatore; embedding `text-embedding-3-large` a 1.536 dimensioni per il film index, `text-embedding-3-small` solo per il backend legacy).
- Vector store: **solo Qdrant** (`qdrant-client` 1.20.0 fissato insieme alla versione del server in `store/settings.py`), collezione **`wikipedia_films_it_v3`** (41.138 punti, un film per punto, 1536 dimensioni, cosine; il film index richiede il server, non `embedded`) nello storage del server `dbVettoriale/qdrant_openai/storage`; `netflix_scout` (42.522 punti, CMU 2012), `wikipedia_films_it` (v1) e `wikipedia_films_it_v2` restano intatte e non si scrivono mai (la v3 non si elimina; il rollback al vecchio RAG è `RAG_BACKEND=legacy`). Modalità `server` (predefinita, `http://127.0.0.1:6333`) | `embedded` | `memory` (solo test), da `CONFIG["rag"]["vectorstore"]["qdrant"]` o dalle variabili `VECTORSTORE_QDRANT_MODE|URL|PATH` (`QDRANT_API_KEY` solo per un server con chiave). Non esiste più nessun altro motore: ChromaDB, `VECTORSTORE_ENGINE` e ogni ritorno a Chroma sono stati rimossi (la vecchia cartella `dbVettoriale/openai`, se presente, è un dato inutilizzato che si può cancellare a mano). Storia, parità, ricostruzione e prove: `docs/qdrant_migration/README.md`.
- Retrieval: **un solo retriever denso** sul film index (`tool/rag/FromQueryEmbeddingToRes/film_index/`), con filtri, esclusioni, penalità semantica e riordino LLM; nessun RRF, nessuna fusione, nessun ripiego. BM25/`hybrid.py` e Cohere esistono solo nel backend legacy e si rimuoveranno dopo la verifica della stabilità (decisione del lessicale: filtro full-text Qdrant, hit@5 1,00 contro 0,47, `tool/RAGWikipediaFilm/eval/results/LEXICAL_REPORT.md`).
- DB MovieLens: `sqlite3` della stdlib; CSV e DB in `movie_db/data/` (ignorata da git, read-only a runtime).
- Riordino: LLM (`gpt-5.6-sol` senza ragionamento, 40 candidati, fino a 1.500 caratteri di trama; ~3 s) nel film index; `cohere` (`rerank-v3.5`) o LLM solo nel backend legacy.
- TMDb: `urllib.request` della stdlib (nessuna dipendenza nuova), chiave da `.env` (`VUE_APP_TMDB_API_KEY`, `VUE_APP_TMDB_BASE_URL`).
- YouTube: `urllib.request` e `zoneinfo` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), chiave `YOUTUBE_API_KEY` da `.env`, letta solo da `tool/youtube/auth.py`.
- Wikipedia: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API pubblica MediaWiki), User-Agent con repository e contatto in `tool/wikipedia/settings.py` (policy Wikimedia).
- OMDb: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), chiave `OMDB_API_KEY` da `.env`, letta solo da `tool/omdb/auth.py`. Termini: uso personale e non commerciale (contenuto CC BY-NC 4.0; vietati indici e ridistribuzione), vedi «Tool OMDb».
- TVmaze: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API pubblica `https://api.tvmaze.com`), User-Agent con repository e contatto in `tool/tvmaze/settings.py`; dati CC BY-SA, attribuzione con link (vedi «Tool TVmaze», dubbi legali ancora aperti).
- Wikidata: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API MediaWiki di ricerca delle entità e Wikidata Query Service, SPARQL), User-Agent con repository e contatto in `tool/wikidata/settings.py`; dati CC0 (vedi «Tool Wikidata»).
- Modelli dati: `pydantic` v2. Loader: `pypdf`, `python-docx`, `beautifulsoup4`, `markdown-it-py`.
- Test: `pytest`. Nessun linter o formatter configurato.

**Flusso a runtime** (`app.py`)
```
input + ultimi classifier_context_messages della history → classify_query_domain (gpt-4o-mini, JSON) ──non cinema──→ rifiuto secco (`block_reply` dello stesso classificatore, nella lingua dell'ultimo messaggio; ripiego fisso it/en/de, altrimenti inglese), senza stadio, storia né riquadro
                         │ cinema
                         ▼
LLMOrchestrator (orchestrator.py) → sceglie il tool → RagTool.run → run_rag → run_film_index (parser LLM → ricerca densa con filtri/esclusioni/penalità → riordino LLM, nessuna generazione) → TmdbRagEnricher (locandina e id TMDb dei soli film restituiti, per IMDb id)
                                                   oppure MovieDbTool.run → parser LLM → MovieDbQuery → SQL whitelistato read-only
                                                   oppure TmdbTool.run → TmdbToolInput validato → risoluzione ID → endpoint fissi (budget per turno) → contesto limitato
                                                   oppure YoutubeTool.run → YoutubeToolInput validato → search.list per categoria (limite per turno) → un videos.list → filtro di pertinenza → metadata + trace
                                                   oppure OmdbTool.run → OmdbToolInput validato → (ricerca per titolo) → identificazione certa → record per IMDb ID → punteggi con stato (budget per turno, nessuna cache) → metadata + trace
                                                   oppure WikipediaTool.run → WikipediaToolInput validato → ricerca (anteprime) o articolo intero scaricato una volta (cache) → sezioni consegnate fino al budget di contesto del turno → metadata + trace + `follow_up` (cosa è stato letto e cosa no)
                                                   oppure WikidataTool.run → WikidataToolInput validato → (ricerca entità per titolo) → identificazione certa (anno, regista, ID IMDb/TMDb) → relazioni dichiarate con query SPARQL predefinite (budget per turno, nessuna cache) → metadata + trace + `follow_up`
                         ▼
il planner può concatenare altri tool nello stesso turno (fino a max_tool_calls_per_turn, ogni passo usa i dati dei precedenti) → l'orchestratore genera la risposta finale (final_instructions + tool_final_instructions di ogni tool usato) → history → compattazione oltre memory_window_size

`TurnResult.timings` (fase 8, solo misura, nessun canale lo mostra): classificatore, chiamate del planner (ms e token di ciascuna), tool (ms, SQL locale, richieste HTTP), risposta (ms, primo testo, token), totale.

Ogni step (query riscritta, tool scelto, esito e secondi, trace del tool, fallback) va al TurnObserver del canale MENTRE accade; il terminale lo stampa subito (storia in poche frasi + blocco del tool), il web riceve gli stessi dati in JSON. La risposta finale è UNA chiamata in streaming: il testo arriva all'osservatore con `answer_delta` mentre il modello scrive (anche il messaggio di blocco, il chiarimento e il ripiego arrivano come delta); alla fine present(..., streamed=True) chiude solo la riga e dà l'avviso di compattazione.
```

**Pattern architetturali**
- **Film index (il RAG attivo, `CONFIG["rag"]["backend"] = "wikipedia"`, integrato il 2026-11-05)**: collezione `wikipedia_films_it_v3` (41.138 film con la trama di Wikipedia italiana fino a novembre 2026, meno completa dopo il 2019; `text-embedding-3-large` 1.536 dimensioni), UN solo retriever denso, nessun RRF né fusione né ripiego sul vecchio indice. `run_rag` smista su `backend` e restituisce lo stesso `RagResult`. Il planner passa la richiesta INTERA in `arguments.query` (positivo e negativo insieme; schema `FilmIndexToolInput`: `query` e `k_finale`, niente `search_mode`); `film_index/parser.py` (una chiamata, `gpt-5.6-luna`) ne ricava `Signals` (descrizione voluta it/en, film citati con riassunto, film e franchise da escludere, tratti da evitare scritti IN POSITIVO, generi/formati, anni, paesi, registi, attori, parole rare, contraddizione). `film_index/search.py`: filtri positivi lato Qdrant (anno, paese, regista e attore normalizzati, parole rare con l'indice full-text) → pool di 300 → via i film citati, i franchise (per id `franchise_ids` e per nome), i generi esclusi (mai un genere anche voluto o che etichetta più dell'8% del catalogo) e i formati → penalità `cos(r, voluto) − 0,5·max cos(r, tratto da evitare)` → riordino LLM dei primi 40 (`gpt-5.6-sol`, nessun ragionamento, fino a 1.500 caratteri di trama; se fallisce resta l'ordine della penalità, nota `reorder_failed`). Un film citato assente dal catalogo è descritto all'embedder con il riassunto del parser: **non si scrive mai su Qdrant** (flusso del catalogo TMDb e flusso dei riferimenti del vecchio RAG non si usano). Se il parser fallisce si cerca la richiesta semplice senza esclusioni e la nota `parser_failed` arriva alla risposta. `metadata.films` porta alla risposta titolo, titolo originale, anno, regia, cast, paesi e durata (mai id né URL); `search_notes` porta contraddizione, filtri senza risultati e fallimenti. Tutti i parametri sono in `CONFIG["rag"]["film_index"]`. **Misure** (`tool/RAGWikipediaFilm/EVAL_REPORT.md`, `eval/results/OPTIMIZATION_REPORT.md`): su 56 domande con esclusioni, 4% di violazioni e 80–85% di film validi contro 10% e 66% del vecchio RAG come girava; risposte 96 a 27 nel confronto cieco; i filtri su persone, anno e paese 82–95% di film validi contro 11%; riordino da ~10 s a ~3 s con le stesse violazioni (gpt-5.6-sol senza ragionamento, 1.500 caratteri); il solo id non basta (68% di violazioni su titoli e franchise), il franchise per id batte quello per nome, la sottrazione di vettori non batte la penalità, i filtri di genere non servono per i tratti. Limiti noti: `franchise_id` su 4.049 film (10%), `genres` è testo libero, il rilevamento delle contraddizioni è stocastico.
- **Backend legacy (rollback, `RAG_BACKEND=legacy` o `build_runtime_config(LEGACY_RAG_OVERRIDES)`)**: il vecchio RAG (CMU 2012, `netflix_scout`, parser inglese, BM25/RRF, Cohere, catalogo e film di riferimento) resta nel codice (`tool/rag/FromQueryEmbeddingToRes/{retrieval,rerank,hybrid,constraints,references,reference_flow,vectorstore,...}.py`, `store/`, `legacy_rag_prompts.py`) SOLO per tornare indietro: si accende al posto del film index, mai insieme. `LEGACY_RAG_OVERRIDES` ripristina anche la regola 3, le regole di risposta sul completamento TMDb per titolo e la copertura al 2012. Verificare la stabilità del film index prima di eliminarlo (elenco dei componenti rimovibili in `tool/RAGWikipediaFilm/PROGRESS.md`).
- **Impostazioni utente (`preferences/`) — PREVALGONO sulla richiesta (decisione del proprietario, 2026-11-05)**: sei campi (spoiler, lunghezza, tono, approccio, tipo di contenuto, fonti preferite), applicati **per turno** e solo dal web (`preferences=None` nel terminale: nessun conflitto, prompt identici). **Regola**: ogni impostazione, valori di default compresi, vince su una richiesta esplicita che la contraddice; la PRIMA frase della risposta dichiara il conflitto e quale impostazione prevale, poi si serve la parte compatibile e non si esegue mai la parte in conflitto. Per `preferred_sources` è conflitto solo la richiesta esplicita di un'altra fonte; `content_type=both` non confligge mai. **Come è applicata**: (1) il planner (STESSA chiamata di `_plan_first`, nessuna chiamata in più) riceve tutte le impostazioni come vincolanti (`preferences/behavior.py:PLANNER_INTRO`) e dichiara i conflitti nel campo `conflicts: [{setting, requested}]`; pianifica solo la parte compatibile, e con `tool_name` null e conflitti non parte alcun tool (`CONFLICT_ONLY`: la risposta è la sola frase fissa, nessuna chiamata di risposta); con spoiler disattivati e richiesta del finale la parte compatibile esiste sempre (la ricerca del film: la risposta dà premessa e contesto). (2) **Guardia deterministica** (`preferences/policy.py`, `SettingsPolicy.check_step`, chiamata dall'orchestratore PRIMA di ogni tool): con `content_type=series` `rag_search` e `movie_db_search` sono vietati e le richieste TMDb su film (`movie_details`, `movie_collection`, `discover_movies`, `search` kind movie, `trending`/`chart` movie) sono tolte; con `film` sono vietati `tvmaze_search` e le operazioni TMDb su serie; un passo vietato non gira (fallback `blocked_by_setting`, il planner ne sceglie uno compatibile, al massimo 2 volte; poi `partly_blocked_by_setting` se si tolgono solo alcune richieste). Un test tiene i nomi delle operazioni allineati a `TmdbOperation`. (3) **Frase di conflitto fissa** (it/en/de, ogni altra lingua legge l'inglese) emessa PER PRIMA come `answer_delta` e fatta partire la risposta (`_generate_final_answer(answer_prefix=)`; nel web è parte di `answer`), quindi non dipende dal modello; il modello riceve `answer_note` (ignora la parte in conflitto, non ripetere la frase). (4) `TurnResult.settings_conflicts` e `planning.settings_conflicts` riportano i conflitti; la storia racconta i passi vietati. Il tono non si applica ai messaggi fissi (chiarimento, blocco non-cinema, frase di conflitto). Il frontend non cambia. Test: `tests/test_settings_precedence.py`, `tests/test_preferences*.py`; verifica live con l'applicazione reale: `python -m tool.RAGWikipediaFilm.eval.conflicts` (24 casi: conflitti per ogni campo, controlli senza conflitto, guardia). Le istruzioni delle impostazioni stanno in `preferences/behavior.py` e non in `CONFIG`. Resta vero: la fonte `interviews` per un film identificato fa aggiungere un passo `youtube_search` (costo: fino a `max_searches_per_turn`); le impostazioni sono richieste al modello per la forma della risposta (gli spoiler non sono un filtro sui dati: trame, sezioni Plot e titoli arrivano interi al modello). **Limite noto**: con i default vincolanti molte richieste legittime («in breve», «dimmene uno solo», un tono diverso) danno un conflitto; il rilevamento è un giudizio del planner.
- **Config-driven**: tutti i parametri (modelli, k, backend, prompt) vivono in `CONFIG` in `app.py`. Niente valori hardcoded nei moduli: passa `config` come dict. Gli override passano da `build_runtime_config(overrides)`.
- `_resolve_runtime_config` normalizza la config RAG (modello di embedding iniettato nella config Qdrant, default della conversazione): chiamala prima di accedere a vectorstore ed embedding.
- **Contratto dei tool**: ogni tool rispetta il `Tool` Protocol (`name`, `description`, `input_schema`, `run(*, query, params, conversation_history) -> dict`). `input_schema` deriva da un modello Pydantic (`model_json_schema()`). Un nuovo tool vive in `tool/<nome>/` (mai nella root), con import relativi e senza importare altri tool, presenter o canali (`tests/test_tool_package.py`), e si registra in `build_app` e in `CONFIG["orchestrator"]["allowed_tools"]`, senza toccare il core.
- **Separazione dei ruoli**: `RagTool`/`run_rag` restituiscono solo evidenza strutturata (`chunks` + `metadata` + `trace`); la risposta finale la genera solo l'orchestratore.
- **Avanzamento in tempo reale**: il turno è sincrono, quindi senza osservatore l'utente non vede nulla finché `LLMOrchestrator.run` non ritorna (era la causa del terminale muto). `handle_query(..., observer=)` e `run(..., observer=)` accettano un `TurnObserver` (`turn.py`: `step(TraceStep)` e `status(stage)`): l'orchestratore emette gli step **mentre accadono** (`query_rewrite`, per ogni tool `tool_selection` con `purpose` e `arguments` **prima** della chiamata, poi `tool_outcome` con `elapsed_ms`/`status`/`reason` e la trace del tool, `planning` per ultimo) e `status(answering)` prima della risposta finale; un osservatore che solleva non rompe il turno. `TurnResult.steps` e `TurnResult.story` sono gli stessi che vede l'osservatore (`_TurnRecorder` in `app.py`); un orchestratore finto nei test deve emettere gli step (`tests/turn_support.py:stream_decision`). Ogni tool mette in `result["outcome"]` (`turn.tool_outcome`: `ok|empty|error` + `reason`, fuori da `metadata`) l'esito che la storia racconta; senza `outcome` conta la presenza di `chunks`. I fallback silenziosi (`planner_failed`, `low_confidence`, `unknown_tool`, `next_step_failed`, `max_tool_calls`, `answer_failed`) stanno in `decision["planning"]["fallbacks"]` e la storia li dice solo quando accadono.
- **Terminale e web uniformi**: stesso contenuto, formato diverso. Ogni step ha una vista in `presenters/*_view.py` (testi it/en, dati) e i due canali ne cambiano solo la forma; la storia (`story_view.StoryBuilder`) è un'unica sequenza di `StoryLine(level, text, tool)` (il terminale aggiunge l'emoji per `level`, il web lascia l'icona al frontend; dopo `MAX_OK_LINES` esiti positivi restano solo i problemi). Gli step di flusso (`classification`, `query_rewrite`, `tool_selection`, `tool_outcome`, `planning`) sono raccontati dalla storia e non hanno renderer né serializer; ogni altro kind deve stare sia in `STEP_RENDERERS` sia in `STEP_SERIALIZERS` (`tests/test_presenter_parity.py`). Un nuovo tool aggiunge la vista condivisa, il renderer terminale e il serializer web.
- **Risposta finale in streaming** (`LLMOrchestrator._generate_final_answer`): sempre `responses.create(stream=True)`, una sola chiamata, mai una seconda. Gli eventi dell'SDK (`response.output_text.delta`, `completed`, `incomplete`, `failed`, `error`, refusal) sono letti in `_consume_stream`; il testo va a `observer.answer_delta`. Senza `final_output` (terminale) i delta sono il testo; con `final_output` (web) i delta grezzi sono JSON e passano da `AnswerFieldStream` (nome del campo da `final_output["answer_field"]`), quindi il canale vede solo il testo di `answer` già decodificato. `answer` e `lists` autorevoli vengono dal parse del JSON completo; lo schema strict ha `answer` PRIMA di `lists` (test) per lo streaming progressivo, ma l'ordine reale del modello non è dimostrato offline (`live_stream_check`). Se lo stream fallisce (incomplete/failed/errore/refusal/JSON non valido): dopo alcuni delta la risposta è il testo già mostrato (`lists: []`), senza delta il ripiego esistente (anch'esso emesso come delta), in entrambi i casi fallback `answer_failed`; la cronologia contiene ciò che l'utente ha visto. Lo step `planning` esce PRIMA della risposta (parti non cercate prima del testo); solo `answer_failed` ne produce un secondo, minimo. `handle_query` tiene la history intera se la compattazione fallisce. Terminale: `TerminalObserver.answer_delta` stampa il riquadro al primo testo non bianco e poi i pezzi; `render(streamed=True)` non ristampa la risposta. Web: il frontend concatena i `answer_delta`; `answer_end.replace` è null se `streamed.strip() == final.strip()`, altrimenti la risposta intera strippata.
- **Server HTTP/SSE (`web_api/`)**: il turno è sincrono e invariato; gira in `asyncio.to_thread` in una task INDIPENDENTE dal client. Commit della history (`finish_turn`, unico punto) quando `handle_query` ritorna, anche se il client è sparito; eccezione → history invariata; la conversazione resta `busy` fino alla fine reale del lavoro (409 nel frattempo); nessuna cancellazione del turno; alla disconnessione la sottoscrizione si chiude e gli eventi successivi sono scartati (la coda non cresce). Nessuna autenticazione né rate limit, per scelta (portfolio, budget limitato sulla chiave backend). Un solo worker.
- **Il nucleo non stampa**: `handle_query` produce un `TurnResult` con gli step (`trace` dei tool inclusa). L'output sta solo in `presenters/<canale>/<tool>/` (`rag`, `db`, `api`); fuori dalle cartelle dei tool solo il collante del flusso e le viste condivise; un nuovo tool aggiunge `presenters/terminal/<tool>/` e `presenters/web/<tool>/` (struttura verificata da `tests/test_tmdb_presenters.py`). Il canale (`OutputChannel`) lo dichiara l'entry point: `python app.py` → `terminal`, la futura route FastAPI → `web`. Niente `print` fuori da `presenters/terminal/` (eccezioni: builder offline, loop legacy in `chat.py`).
- **Query autonoma per i follow-up**: nella stessa chiamata LLM con cui sceglie il tool, l'orchestratore (`_plan_turn`) riscrive la domanda in modo autonomo usando la history (`standalone_query`) e la passa a **qualunque** tool, anche con `required_tools` o fallback. Senza history o se l'LLM fallisce si usa la domanda originale. Per `rag_search` la ricerca parte sempre dalla `standalone_query` (le parole dell'utente); `arguments.query` del planner arriva al parser dei segnali solo come `query_hint` ("Planner rewrite"), perché può essere vaga (caso reale: "Film simili a Mare dentro, che affrontino temi e atmosfere analoghi"); il trace `retrieval` riporta entrambe. La history va passata **intera e invariata** (niente finestre scorrevoli): un prefisso stabile permette al prompt caching del provider di riusarla.
- **Lingua del turno** (decisione del 2026-10-27; `turn.py`: `normalize_language`, `label_language`, `language_name`): fa fede **solo l'ultimo messaggio** dell'utente, mai la lingua prevalente né la history (che serve solo ai riferimenti): si può cambiare lingua al messaggio 10 e la risposta 11 segue. Il classificatore restituisce `language` (codice ISO 639-1, al posto di `is_italian`; `query_language` non esiste più); `_validate_classification` lo normalizza (`de-DE`→`de`, «German»→`de`) e un valore non valido o assente non solleva: `resolve_language` ripiega sui marcatori it/en e poi su `en`. `detect_language_markers` (parole funzionali it/en) corregge il modello **solo** quando questo ha detto it/en o nulla, mai su una lingua terza (una frase tedesca attorno a un titolo italiano resta tedesca). Un messaggio senza contenuto linguistico (solo un titolo) segue, per istruzione al modello, l'ultimo messaggio utente precedente: unico caso in cui la history conta, non dimostrabile offline. `TurnResult.language` e `answer_end.language` sono una stringa libera. **Testi fissi** (storia, etichette degli step, titoli RAG, blocchi del terminale, ripiego del blocco e `NO_ANSWER_TEXTS`) esistono in it/en/de; ogni altra lingua legge l'inglese (`label_language`) mentre il testo libero è scritto dal modello nella lingua giusta. Aggiungere una lingua = una colonna in ogni tabella (`presenters/*_view.py`, `presenters/terminal/texts.py`, `orchestrator.NO_ANSWER_TEXTS`, `app.NON_CINEMA_BLOCK_MESSAGES`; `tests/test_turn_language.py` verifica che le colonne siano complete). **Prompt**: `run(answer_language=)` aggiunge UNA riga dinamica alla risposta finale (dopo le regole dei tool e prima delle impostazioni utente, che governano ancora la forma) e una al planner (lingua della domanda di chiarimento); senza lingua i prompt sono identici a prima. Banner, prompt `Tu >` e saluto del terminale non appartengono a un messaggio e restano italiani. Specifica per il front-end: `docs/frontend_handoff_language.md`.
- **Contesto del classificatore**: `handle_query` passa a `classify_query_domain(query, history)` gli ultimi `CONFIG["orchestrator"]["classifier_context_messages"]` messaggi della history. Il guardrail gira prima della riscrittura `standalone_query`: senza contesto un follow-up come "ne puoi trovare 3 più recenti?" verrebbe bloccato. La history serve solo a risolvere riferimenti impliciti; si classifica sempre l'ultima query. Il prompt considera cinematografiche anche le richieste su un film già citato (trama, dettagli, traduzione) in qualsiasi lingua: chiedere la risposta in un'altra lingua non è un jailbreak (prima "Could you get in english the plot from the movie you just advised?" veniva bloccata). Lo step `classification` resta nel trace ma non viene stampato (né a terminale né sul web): un blocco mostra solo il messaggio di blocco. **Lingua**: vedi «Lingua del turno» qui sotto.
- **Trace dei tool**: ogni tool restituisce `"trace": [{kind, title, data}]` fuori da `metadata` (che finisce nel prompt). Un `kind` nuovo ha il renderer nella cartella del suo tool (`presenters/terminal/<tool>/renderer.py`, su una vista condivisa) e va registrato in `presenters/terminal/renderer.py:STEP_RENDERERS` (firma `(step, language)`, `language` = `TurnResult.language`) **e** il serializer in `presenters/web/payload.py:STEP_SERIALIZERS`, altrimenti viene stampato col fallback generico.
- **Testo dell'embedding (SOLO backend legacy)**: il corpus è composto da trame in inglese. Il parser `_extract_query_signals` (`retrieval.py`) produce `QuerySignals` in inglese con `semantic_query` (la frase su cui si fa l'embedding) e `genres` (vocabolario del corpus). `vectorstore.search` fa l'embedding di `semantic_query`, altrimenti della query originale, **mai** del join dei `positive_signals`: un insieme di keyword italiane faceva finire il retrieval su film italiani o storici. Il genere non viene indicizzato nel testo: entra nel ranking con il boost `retrieval.genre_boost` sul pool di `retrieval.fetch_k` e nel documento passato al reranker (`rerank._documento_per_rerank`). Lo step `retrieval` del trace riporta `embedded_text` e `signals`. Il reranker riceve `compose_rerank_query`: `semantic_query` (altrimenti la query) più "Must match: …" con i segnali positivi e i generi richiesti le cui parole chiave mancano dalla frase (decennio, paese, genere, ambientazione), esclusi i segnali sulla forma della risposta (voti, recensioni). Prima la frase semantica perdeva vincoli (caso 20: "1950s"). A/B controllato (stesso pool, 36 chiamate Cohere): violazioni verificabili 20 con la query italiana, 21 con la sola semantica, 16 con la query composta, mai peggiore della migliore in 12 confronti. Il parser dei segnali deve conservare paese, decennio, generi e ambientazione e descrivere i temi di un film citato come riferimento invece di scrivere "simile a X". `QuerySignals.excluded_genres` ("senza fantascienza") esclude i chunk sui metadati `genres` (parole intere); `hard_exclusions` filtra solo i titoli. `constraints.constraint_report` calcola (nello step `rerank` del trace, chiave `constraints.checks`) uno stato per vincolo e per film: `verified` (metadati: generi, anno/decennio), `probable` (tutti i termini chiave nella trama), `not_verifiable` (finali, tono, emozioni, termini assenti: l'assenza non prova nulla), `contradicted` (metadati o frase esplicita nella trama); un requisito negato ("non-tragic ending") non è mai `probable` e nessun segnale debole scarta un film; un segnale positivo che ripete un genere richiesto non riceve un secondo stato. La nazionalità ("Japanese") è origine produttiva, non trama: `verified` solo se i generi del catalogo la nominano ("Japanese Movies"), altrimenti `not_verifiable` (un personaggio giapponese non basta). Al prompt arriva `metadata.constraints_summary` (`constraint_summary`): una riga per film e vincolo con cosa si può affermare; il report completo resta nel trace. `tests/answer_checks.py` controlla una risposta finale contro gli stati (usato da `tests/test_answer_constraints.py` su risposte reali registrate e dagli script di valutazione e2e). `hard_exclusions` diventano controlli `title_exclusion` su titolo e cast. Lo step `rerank` riporta `rerank_query` e `constraints`. Dopo Cohere/LLM `_rerank(..., signals=)` chiama `constraints.demote_contradicted`: riordino stabile che mette dopo i film contraddetti dai soli metadati (genere, genere escluso, decennio, titolo escluso), senza scartarli né usare trama o tono. A/B reale del 2026-10-26 (5 casi, stesso pool di 10, 15 chiamate Cohere): violazioni nei top 3 4→3 con ciascuna delle tre query; il caso 20 resta (nessun candidato conforme nel pool), campione piccolo e metrica identica al criterio del riordino.
- **DB MovieLens read-only**: il modello non scrive mai SQL. Il parser riempie un `MovieDbQuery` (enum `MovieDbOperation`, `extra="forbid"`); `sql/queries.py` compone solo frammenti costanti con parametri bind; la connessione è `mode=ro` + `PRAGMA query_only` + authorizer (`guard.py`). Una nuova operazione = valore dell'enum + builder in `QUERY_BUILDERS` + caso in `harness/evaluation/cases.py`. Solo `harness/ingestion/` scrive il DB; `app.py` e `tool/movie_db/` non importano `movie_db/harness/` (verificato da `tests/test_movie_db_app.py`).
- **Trace del tool DB**: un solo step `db_query` con `{"queries": [{"sql", "params"}]}`: niente righe, limiti o path. Terminale e web leggono lo step solo tramite `presenters/db_view.py`, così i due canali mostrano le stesse query.
- **Valutazioni live**: `run_eval --live-parser` e `run_routing_eval --live` sono gli unici controlli che consumano crediti; non sono test pytest (le loro parti offline sono in `tests/test_movie_db_eval.py` e `tests/test_movie_db_routing_eval.py`). Il routing eval chiama solo `classify_query_domain` e `_plan_turn` con un client che registra l'output grezzo, senza modificare l'orchestratore: un fallback silenzioso a `rag_search` è un fallimento. Per i casi TMDb gli `arguments` del planner sono validati come `TmdbToolInput` (senza HTTP) e almeno una richiesta deve rispettare `expected_request` (operazione, frammenti dei campi, facet); per i casi YouTube sono validati come `YoutubeToolInput` e devono rispettare `expected_video` (frammento del titolo, `kinds` richieste più le `extra_kinds` tollerate, e `year`, `director`, `cast`, `alternative_titles` vuoti salvo i valori elencati in `allowed`, cioè presenti nella richiesta o nella history); `--tool` limita il run ai casi di un tool. Tra `top_rated` e `by_genre_year` l'equivalenza vale solo con genere e senza anni e con SQL e parametri identici. - **Ciclo multi-tool** (`LLMOrchestrator.run`): la regola "un solo tool per turno" non esiste più. Il primo `_plan_first` (la stessa chiamata di prima, `_plan_turn` ne è il wrapper a tupla usato dal routing eval) sceglie il primo tool ed elenca le `parts` della richiesta (`{part, tool}`; voci con tool sconosciuto scartate); serve un altro passo se `more_steps` è true **o** una parte ha un altro tool. Solo allora `_plan_next` fa una chiamata in più, con i risultati già ottenuti (riassunto fino a `STEP_SUMMARY_CHARS`) e le parti ancora senza tool eseguito, e ritorna il passo successivo o `{"done": true}`. Un turno a un solo tool costa quindi le stesse chiamate LLM di prima. Il ciclo finisce con `complete` (nessuna parte pendente), `done`, `repeated_step`, `unknown_tool_or_low_confidence`, `planner_failed`, `required_tools`, `max_tool_calls` (motivo in `decision["planning"]["stop_reason"]`); prima era: `done`, passo ripetuto (stesso tool e argomenti), passo sconosciuto o con `confidence` sotto soglia, errore del planner (mai un fallback a `rag_search` dopo il primo passo: si risponde con ciò che c'è), `required_tools` (un solo passo) o `CONFIG["orchestrator"]["max_tool_calls_per_turn"]` (10). Il chiarimento è solo al primo passo. Le parti pendenti a fine turno arrivano alla risposta finale come "Parti della richiesta NON eseguite" (da dichiarare "non cercate", mai "non trovate"; caso reale 2026-10-24: intervista mai cercata e riportata come non trovata) e lo step `planning` (`STEP_PLANNING`, solo se i tool sono più di uno, resta una parte pendente o c'è un fallback) le racconta all'utente nella storia ("Non ho cercato: …"). La risposta finale riceve tutti i risultati (`tool_results`, un blocco per tool) e le `tool_final_instructions` di ogni tool usato. `decision` ha `tool` e `result` del primo passo, più `tools` e `calls` (`{tool, arguments, result}`); l'orchestratore emette per ogni chiamata, mentre accade, `tool_selection` (prima del tool), `tool_outcome` (dopo) e la trace del tool (vedi "Avanzamento in tempo reale"), `TurnResult.tools` elenca i tool: i presenter mostrano solo i tool eseguiti (nessun output RAG se il RAG non è stato chiamato). I limiti per turno (`tmdb.max_calls_per_turn`, `you_tube.max_searches_per_turn`) contano sul `turn_id`, non sulla run. Errori del tool DB: `metadata.error_kind` `unsupported_request` (nulla nella whitelist, es. filtro per attore) o `parser_failed`, con regola in `final_instructions`.
- **Offerta di altro (`follow_up`)** (`turn.RESULT_FOLLOW_UP`, `orchestrator._follow_up`): un tool può mettere nel risultato (fuori da `metadata`, quindi fuori dal prompt finale) `follow_up = {"available": bool, "reasons": [str], "summary": str}`. Se `available` è vero il ciclo chiama `_plan_next` anche con `more_steps` falso e senza parti pendenti; `_summarize_call` mostra al planner `summary` al posto di `Metadata` troncato a `STEP_SUMMARY_CHARS`; `_plan_next` aggiunge una riga che dice quali motivi ci sono e chiede se ciò che c'è basta (altrimenti il passo successivo, altrimenti `done`). La sufficienza la giudica il planner LLM sulla richiesta e su `summary` (outline, cosa è stato letto e cosa no), non una soglia del tool. Chi non produce `follow_up` costa le stesse chiamate di prima (`tests/test_orchestrator_follow_up.py`, parametrizzato). Freni: `done`, `repeated_step` (stessi tool e argomenti), `max_tool_calls_per_turn`, e il tool smette di offrire quando non ha più budget (chiamate o contesto) o dopo `rate_limited`. Lo usano `wikipedia_search` e `tmdb_search`: quest'ultimo lo offre (motivi `not_found`, `unverified_match`, `empty`; riassunto con le richieste non risolte) quando una richiesta non trova nulla, così il planner può passare a un altro tool invece di chiudere sul fallimento (errori di limite, chiave o rete non si offrono); i risultati riusciti non hanno la chiave. **Fine del ciclo** (`_plan_next`, contratto in `orchestrator.NEXT_STEP_FORMAT`, aggiunto alle istruzioni di quella sola chiamata; classificazione pura `_classify_next_step`): conclusione esplicita = `{"done": true}` (booleano vero) oppure un segnale di stop **definito dal contratto** (`tool_name` nullo, vuoto o `done`/`none`/`stop`) non contraddetto da `done: false` né da `more_steps: true`; in tal caso `stop_reason = "done"`, nessun fallback e nessun avviso. Risposta **incompleta o contraddittoria** (`{}`, solo `confidence`, `done: false` senza tool, `done` stringa o numero, `tool_name` nullo con `more_steps: true`, `tool_name` non stringa) = `stop_reason = "planner_incomplete"` con l'avviso `next_step_failed`. Restano errori con avviso: testo non JSON o non oggetto (`planner_failed`), tool nominato ma non ammesso o confidenza sotto soglia (`unknown_tool_or_low_confidence`). `decision["planning"]["planner_output"]` (e lo step `planning`) registra cosa ha risposto il planner **senza testo libero né argomenti** (`_planner_detail`: nomi delle sole chiavi note, altre come `<key>`; `done`/`confidence`/`more_steps` scalari, stringhe come `<str>`; `tool_name` solo se è un tool dell'app o una parola di stop). Nel test live del 2026-10-25 il vecchio controllo (`done is True` e basta) dava l'avviso spurio «Non ho potuto pianificare il passo successivo» in 6 turni su 7 con Wikipedia; la causa (probabilmente `tool_name: null` nel formato del primo passo, imposto dal system prompt di `_plan_next`) non era verificabile perché l'output grezzo non era registrato.
