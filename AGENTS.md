# AGENTS.md — NetflixScout

Guida operativa per agenti IA. Leggila prima di modificare il codice.

## 1. Contesto del Progetto

**Scopo**: assistente conversazionale da terminale che consiglia film usando RAG sul CMU Movie Summary Corpus, un DB SQL locale read-only di MovieLens 32M (voti, classifiche, generi per anno, tag), l'API TMDb (dati aggiornati: cast, uscite, streaming, serie, persone, trending) e la YouTube Data API v3 (video su un film identificato: interviste a regista e cast, making-of, dietro le quinte, commenti degli autori). Risponde solo a domande cinematografiche (classificatore anti off-topic e anti jailbreak).

**Stack**
- Python 3.11 (`.venv/` locale), nessun `pyproject.toml`: le dipendenze stanno in `requirements.txt` (versioni pinnate).
- LLM ed embedding: `openai` (Responses API + Chat Completions per il classificatore), `sentence-transformers`/`torch` per gli embedding locali.
- Vector store: `chromadb` persistente in `dbVettoriale/<backend>/` (`openai` | `local`), similarità cosine.
- Retrieval: semantico, BM25 (`rank-bm25`), ibrido con RRF.
- DB MovieLens: `sqlite3` della stdlib; CSV e DB in `movie_db/data/` (ignorata da git, read-only a runtime).
- Rerank: `cohere` (`rerank-v3.5`) oppure LLM.
- TMDb: `urllib.request` della stdlib (nessuna dipendenza nuova), chiave da `.env` (`VUE_APP_TMDB_API_KEY`, `VUE_APP_TMDB_BASE_URL`).
- YouTube: `urllib.request` e `zoneinfo` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), chiave `YOUTUBE_API_KEY` da `.env`, letta solo da `tool/youtube/auth.py`.
- Wikipedia: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API pubblica MediaWiki), User-Agent con repository e contatto in `tool/wikipedia/settings.py` (policy Wikimedia).
- Modelli dati: `pydantic` v2. Loader: `pypdf`, `python-docx`, `beautifulsoup4`, `markdown-it-py`.
- Test: `pytest`. Nessun linter o formatter configurato.

**Flusso a runtime** (`app.py`)
```
input + ultimi classifier_context_messages della history → classify_query_domain (gpt-4o-mini, JSON) ──non cinema──→ messaggio di blocco it/en
                         │ cinema
                         ▼
LLMOrchestrator (orchestrator.py) → sceglie il tool → RagTool.run → run_rag (retrieve + rerank, nessuna generazione) → TmdbRagEnricher (metadati TMDb dei candidati)
                                                   oppure MovieDbTool.run → parser LLM → MovieDbQuery → SQL whitelistato read-only
                                                   oppure TmdbTool.run → TmdbToolInput validato → risoluzione ID → endpoint fissi (budget per turno) → contesto limitato
                                                   oppure YoutubeTool.run → YoutubeToolInput validato → search.list per categoria (limite per turno) → un videos.list → filtro di pertinenza → metadata + trace
                                                   oppure WikipediaTool.run → WikipediaToolInput validato → ricerca (anteprime) o articolo intero scaricato una volta (cache) → sezioni consegnate fino al budget di contesto del turno → metadata + trace + `follow_up` (cosa è stato letto e cosa no)
                         ▼
il planner può concatenare altri tool nello stesso turno (fino a max_tool_calls_per_turn, ogni passo usa i dati dei precedenti) → l'orchestratore genera la risposta finale (final_instructions + tool_final_instructions di ogni tool usato) → history → compattazione oltre memory_window_size

Ogni step (query riscritta, tool scelto, esito e secondi, trace del tool, fallback) va al TurnObserver del canale MENTRE accade; il terminale lo stampa subito (storia in poche frasi + blocco del tool), il web riceve gli stessi dati in JSON. La risposta finale è UNA chiamata in streaming: il testo arriva all'osservatore con `answer_delta` mentre il modello scrive (anche il messaggio di blocco, il chiarimento e il ripiego arrivano come delta); alla fine present(..., streamed=True) chiude solo la riga e dà l'avviso di compattazione.
```

## 3. Linee Guida di Stile e Architettura

**Formattazione**
- PEP 8, indentazione di 4 spazi, righe di circa 100 caratteri, virgole finali nelle chiamate su più righe.
- `from __future__ import annotations` in testa ai moduli nuovi; type hint moderni (`list[dict]`, `str | None`).
- Import relativi dentro `tool/rag/FromQueryEmbeddingToRes/` (`from .models import ...`), assoluti dalla root (`from tool.rag.FromQueryEmbeddingToRes... import ...`).
- Le funzioni private del modulo hanno il prefisso `_`; argomenti keyword-only (`*`) per le API pubbliche (`run_rag`, `Tool.run`).
- Naming misto italiano/inglese **già esistente** (`recupera`, `genera`, `apri_collection`, `indicizza`, `testo`, `k_largo`, `k_finale`): rispetta il nome già usato nel modulo che tocchi, non rinominare.
- Prompt e messaggi per l'utente finale in italiano, docstring ed errori tecnici in inglese.

**Pattern architetturali**
- **Parametri RAG scelti dal planner**: `k_finale` (quanti film chiede l'utente; null = default di `CONFIG["rag"]["retrieval"]`, con `limits.k_finale` min/max). e `search_mode` (null = `semantic`; `hybrid` solo se la richiesta si regge su parole concrete che devono comparire nella trama: personaggio, luogo, oggetto, termine raro, frase tra virgolette; `bm25` da solo non è ammesso e `resolve_retrieval` lo ignora; in hybrid la parte keyword cerca con la `semantic_query` inglese, non con le parole dell'utente, perché il corpus è inglese). `RagToolInput` li espone (`extra="forbid"`); `RagTool.run` li passa a `retrieval_params.resolve_retrieval`, che clampa `k_finale`, tiene `k_finale <= k_largo <= fetch_k`, ignora valori non validi e ogni altra chiave, e lavora su una copia della config. Lo step `retrieval` riporta `retrieval_params` (`effective`, `overridden`). `k_largo`, `fetch_k` e `genre_boost` sono stati provati nello schema del planner (insieme a `search_mode`) e **rimossi**: due A/B live del 2026-10-24 (10 domande, default contro planner) non hanno mostrato alcun beneficio oltre al conteggio (nei casi in cui differivano solo quelli, 3 su 3 uguali; commedie giapponesi anni 50: più violazioni dei vincoli per film; il planner scriveva `genre_boost` anche fuori scala, 1,5–2,0). Il guadagno netto è `k_finale` uguale al numero chiesto (7 migliori, 0 peggiori, 3 uguali nel secondo run; limite: la metrica premia il conteggio corretto, quindi è una prova sul numero di film, non sulla qualità dei titoli). `search_mode` è stato reintrodotto il 2026-10-26 limitato a `semantic`/`hybrid`: e2e reale su 2 domande (personaggio nominato → hybrid, trovato *Hannibal*; tema → semantic); il beneficio di qualità non è misurato con un A/B. Caso di routing in `routing_cases.py`. Valutazione: `routing_cases.py` (`expected_rag`) e `python -m movie_db.harness.evaluation.run_rag_params_eval --live` (A/B, ~10 planner + 20 parser + 20 Cohere, pause di 7 s). Correzione collaterale: `bm25`/`hybrid` leggono la collection a pagine e tengono l'indice in cache (`hybrid.py`; prima `collection.get()` falliva con "too many SQL variables" su 42k chunk).
- **Config-driven**: tutti i parametri (modelli, k, backend, prompt) vivono in `CONFIG` in `app.py`. Niente valori hardcoded nei moduli: passa `config` come dict. Gli override passano da `build_runtime_config(overrides)`.
- `_resolve_runtime_config` normalizza la config RAG (backend effettivo, `db_dir`, default della conversazione): chiamala prima di accedere a vectorstore ed embedding.
- **Contratto dei tool**: ogni tool rispetta il `Tool` Protocol (`name`, `description`, `input_schema`, `run(*, query, params, conversation_history) -> dict`). `input_schema` deriva da un modello Pydantic (`model_json_schema()`). Un nuovo tool vive in `tool/<nome>/` (mai nella root), con import relativi e senza importare altri tool, presenter o canali (`tests/test_tool_package.py`), e si registra in `build_app` e in `CONFIG["orchestrator"]["allowed_tools"]`, senza toccare il core.
- **Separazione dei ruoli**: `RagTool`/`run_rag` restituiscono solo evidenza strutturata (`chunks` + `metadata` + `trace`); la risposta finale la genera solo l'orchestratore.
- **Avanzamento in tempo reale**: il turno è sincrono, quindi senza osservatore l'utente non vede nulla finché `LLMOrchestrator.run` non ritorna (era la causa del terminale muto). `handle_query(..., observer=)` e `run(..., observer=)` accettano un `TurnObserver` (`turn.py`: `step(TraceStep)` e `status(stage)`): l'orchestratore emette gli step **mentre accadono** (`query_rewrite`, per ogni tool `tool_selection` con `purpose` e `arguments` **prima** della chiamata, poi `tool_outcome` con `elapsed_ms`/`status`/`reason` e la trace del tool, `planning` per ultimo) e `status(answering)` prima della risposta finale; un osservatore che solleva non rompe il turno. `TurnResult.steps` e `TurnResult.story` sono gli stessi che vede l'osservatore (`_TurnRecorder` in `app.py`); un orchestratore finto nei test deve emettere gli step (`tests/turn_support.py:stream_decision`). Ogni tool mette in `result["outcome"]` (`turn.tool_outcome`: `ok|empty|error` + `reason`, fuori da `metadata`) l'esito che la storia racconta; senza `outcome` conta la presenza di `chunks`. I fallback silenziosi (`planner_failed`, `low_confidence`, `unknown_tool`, `next_step_failed`, `max_tool_calls`, `answer_failed`) stanno in `decision["planning"]["fallbacks"]` e la storia li dice solo quando accadono.
- **Terminale e web uniformi**: stesso contenuto, formato diverso. Ogni step ha una vista in `presenters/*_view.py` (testi it/en, dati) e i due canali ne cambiano solo la forma; la storia (`story_view.StoryBuilder`) è un'unica sequenza di `StoryLine(level, text, tool)` (il terminale aggiunge l'emoji per `level`, il web lascia l'icona al frontend; dopo `MAX_OK_LINES` esiti positivi restano solo i problemi). Gli step di flusso (`classification`, `query_rewrite`, `tool_selection`, `tool_outcome`, `planning`) sono raccontati dalla storia e non hanno renderer né serializer; ogni altro kind deve stare sia in `STEP_RENDERERS` sia in `STEP_SERIALIZERS` (`tests/test_presenter_parity.py`). Un nuovo tool aggiunge la vista condivisa, il renderer terminale e il serializer web.
- **Risposta finale in streaming** (`LLMOrchestrator._generate_final_answer`): sempre `responses.create(stream=True)`, una sola chiamata, mai una seconda. Gli eventi dell'SDK (`response.output_text.delta`, `completed`, `incomplete`, `failed`, `error`, refusal) sono letti in `_consume_stream`; il testo va a `observer.answer_delta`. Senza `final_output` (terminale) i delta sono il testo; con `final_output` (web) i delta grezzi sono JSON e passano da `AnswerFieldStream` (nome del campo da `final_output["answer_field"]`), quindi il canale vede solo il testo di `answer` già decodificato. `answer` e `lists` autorevoli vengono dal parse del JSON completo; lo schema strict ha `answer` PRIMA di `lists` (test) per lo streaming progressivo, ma l'ordine reale del modello non è dimostrato offline (`live_stream_check`). Se lo stream fallisce (incomplete/failed/errore/refusal/JSON non valido): dopo alcuni delta la risposta è il testo già mostrato (`lists: []`), senza delta il ripiego esistente (anch'esso emesso come delta), in entrambi i casi fallback `answer_failed`; la cronologia contiene ciò che l'utente ha visto. Lo step `planning` esce PRIMA della risposta (parti non cercate prima del testo); solo `answer_failed` ne produce un secondo, minimo. `handle_query` tiene la history intera se la compattazione fallisce. Terminale: `TerminalObserver.answer_delta` stampa il riquadro al primo testo non bianco e poi i pezzi; `render(streamed=True)` non ristampa la risposta. Web: il frontend concatena i `answer_delta`; `answer_end.replace` è null se `streamed.strip() == final.strip()`, altrimenti la risposta intera strippata.
- **Server HTTP/SSE (`web_api/`)**: il turno è sincrono e invariato; gira in `asyncio.to_thread` in una task INDIPENDENTE dal client. Commit della history (`finish_turn`, unico punto) quando `handle_query` ritorna, anche se il client è sparito; eccezione → history invariata; la conversazione resta `busy` fino alla fine reale del lavoro (409 nel frattempo); nessuna cancellazione del turno; alla disconnessione la sottoscrizione si chiude e gli eventi successivi sono scartati (la coda non cresce). Nessuna autenticazione né rate limit, per scelta (portfolio, budget limitato sulla chiave backend). Un solo worker.
- **Il nucleo non stampa**: `handle_query` produce un `TurnResult` con gli step (`trace` dei tool inclusa). L'output sta solo in `presenters/<canale>/<tool>/` (`rag`, `db`, `api`); fuori dalle cartelle dei tool solo il collante del flusso e le viste condivise; un nuovo tool aggiunge `presenters/terminal/<tool>/` e `presenters/web/<tool>/` (struttura verificata da `tests/test_tmdb_presenters.py`). Il canale (`OutputChannel`) lo dichiara l'entry point: `python app.py` → `terminal`, la futura route FastAPI → `web`. Niente `print` fuori da `presenters/terminal/` (eccezioni: builder offline, loop legacy in `chat.py`).
- **Query autonoma per i follow-up**: nella stessa chiamata LLM con cui sceglie il tool, l'orchestratore (`_plan_turn`) riscrive la domanda in modo autonomo usando la history (`standalone_query`) e la passa a **qualunque** tool, anche con `required_tools` o fallback. Senza history o se l'LLM fallisce si usa la domanda originale. Per `rag_search` la ricerca parte sempre dalla `standalone_query` (le parole dell'utente); `arguments.query` del planner arriva al parser dei segnali solo come `query_hint` ("Planner rewrite"), perché può essere vaga (caso reale: "Film simili a Mare dentro, che affrontino temi e atmosfere analoghi"); il trace `retrieval` riporta entrambe. La history va passata **intera e invariata** (niente finestre scorrevoli): un prefisso stabile permette al prompt caching del provider di riusarla.
- **Contesto del classificatore**: `handle_query` passa a `classify_query_domain(query, history)` gli ultimi `CONFIG["orchestrator"]["classifier_context_messages"]` messaggi della history. Il guardrail gira prima della riscrittura `standalone_query`: senza contesto un follow-up come "ne puoi trovare 3 più recenti?" verrebbe bloccato. La history serve solo a risolvere riferimenti impliciti; si classifica sempre l'ultima query. Il prompt considera cinematografiche anche le richieste su un film già citato (trama, dettagli, traduzione) in qualsiasi lingua: chiedere la risposta in un'altra lingua non è un jailbreak (prima "Could you get in english the plot from the movie you just advised?" veniva bloccata). Lo step `classification` resta nel trace ma non viene stampato (né a terminale né sul web): un blocco mostra solo il messaggio di blocco. **Lingua**: la history risolve i riferimenti, non decide la lingua; `detect_language_markers` (parole funzionali it/en) sovrascrive `is_italian` solo con almeno 2 marcatori di una lingua e nessuno dell'altra (prima "Chi l'ha diretto e quanto dura?" dopo un titolo inglese era classificata inglese); altrimenti vale il classificatore.
- **Trace dei tool**: ogni tool restituisce `"trace": [{kind, title, data}]` fuori da `metadata` (che finisce nel prompt). Un `kind` nuovo ha il renderer nella cartella del suo tool (`presenters/terminal/<tool>/renderer.py`, su una vista condivisa) e va registrato in `presenters/terminal/renderer.py:STEP_RENDERERS` (firma `(step, language)`, `language` = `TurnResult.language`) **e** il serializer in `presenters/web/payload.py:STEP_SERIALIZERS`, altrimenti viene stampato col fallback generico.
- **Testo dell'embedding**: il corpus è composto da trame in inglese. Il parser `_extract_query_signals` (`retrieval.py`) produce `QuerySignals` in inglese con `semantic_query` (la frase su cui si fa l'embedding) e `genres` (vocabolario del corpus). `vectorstore.search` fa l'embedding di `semantic_query`, altrimenti della query originale, **mai** del join dei `positive_signals`: un insieme di keyword italiane faceva finire il retrieval su film italiani o storici. Il genere non viene indicizzato nel testo: entra nel ranking con il boost `retrieval.genre_boost` sul pool di `retrieval.fetch_k` e nel documento passato al reranker (`rerank._documento_per_rerank`). Lo step `retrieval` del trace riporta `embedded_text` e `signals`. Il reranker riceve `compose_rerank_query`: `semantic_query` (altrimenti la query) più "Must match: …" con i segnali positivi e i generi richiesti le cui parole chiave mancano dalla frase (decennio, paese, genere, ambientazione), esclusi i segnali sulla forma della risposta (voti, recensioni). Prima la frase semantica perdeva vincoli (caso 20: "1950s"). A/B controllato (stesso pool, 36 chiamate Cohere): violazioni verificabili 20 con la query italiana, 21 con la sola semantica, 16 con la query composta, mai peggiore della migliore in 12 confronti. Il parser dei segnali deve conservare paese, decennio, generi e ambientazione e descrivere i temi di un film citato come riferimento invece di scrivere "simile a X". `QuerySignals.excluded_genres` ("senza fantascienza") esclude i chunk sui metadati `genres` (parole intere); `hard_exclusions` filtra solo i titoli. `constraints.constraint_report` calcola (nello step `rerank` del trace, chiave `constraints.checks`) uno stato per vincolo e per film: `verified` (metadati: generi, anno/decennio), `probable` (tutti i termini chiave nella trama), `not_verifiable` (finali, tono, emozioni, termini assenti: l'assenza non prova nulla), `contradicted` (metadati o frase esplicita nella trama); un requisito negato ("non-tragic ending") non è mai `probable` e nessun segnale debole scarta un film; un segnale positivo che ripete un genere richiesto non riceve un secondo stato. La nazionalità ("Japanese") è origine produttiva, non trama: `verified` solo se i generi del catalogo la nominano ("Japanese Movies"), altrimenti `not_verifiable` (un personaggio giapponese non basta). Al prompt arriva `metadata.constraints_summary` (`constraint_summary`): una riga per film e vincolo con cosa si può affermare; il report completo resta nel trace. `tests/answer_checks.py` controlla una risposta finale contro gli stati (usato da `tests/test_answer_constraints.py` su risposte reali registrate e dagli script di valutazione e2e). `hard_exclusions` diventano controlli `title_exclusion` su titolo e cast. Lo step `rerank` riporta `rerank_query` e `constraints`.
- **DB MovieLens read-only**: il modello non scrive mai SQL. Il parser riempie un `MovieDbQuery` (enum `MovieDbOperation`, `extra="forbid"`); `sql/queries.py` compone solo frammenti costanti con parametri bind; la connessione è `mode=ro` + `PRAGMA query_only` + authorizer (`guard.py`). Una nuova operazione = valore dell'enum + builder in `QUERY_BUILDERS` + caso in `harness/evaluation/cases.py`. Solo `harness/ingestion/` scrive il DB; `app.py` e `tool/movie_db/` non importano `movie_db/harness/` (verificato da `tests/test_movie_db_app.py`).
- **Trace del tool DB**: un solo step `db_query` con `{"queries": [{"sql", "params"}]}`: niente righe, limiti o path. Terminale e web leggono lo step solo tramite `presenters/db_view.py`, così i due canali mostrano le stesse query.
- **Valutazioni live**: `run_eval --live-parser` e `run_routing_eval --live` sono gli unici controlli che consumano crediti; non sono test pytest (le loro parti offline sono in `tests/test_movie_db_eval.py` e `tests/test_movie_db_routing_eval.py`). Il routing eval chiama solo `classify_query_domain` e `_plan_turn` con un client che registra l'output grezzo, senza modificare l'orchestratore: un fallback silenzioso a `rag_search` è un fallimento. Per i casi TMDb gli `arguments` del planner sono validati come `TmdbToolInput` (senza HTTP) e almeno una richiesta deve rispettare `expected_request` (operazione, frammenti dei campi, facet); per i casi YouTube sono validati come `YoutubeToolInput` e devono rispettare `expected_video` (frammento del titolo, `kinds` richieste più le `extra_kinds` tollerate, e `year`, `director`, `cast`, `alternative_titles` vuoti salvo i valori elencati in `allowed`, cioè presenti nella richiesta o nella history); `--tool` limita il run ai casi di un tool. Tra `top_rated` e `by_genre_year` l'equivalenza vale solo con genere e senza anni e con SQL e parametri identici. Ultimo esito: parser 6/6; routing completo 22/22 (11 TMDb, 6 DB, 5 RAG, follow-up inclusi; 44 chiamate LLM) dopo le regole di routing a priorità, poi 23/23 live con il caso di chiarimento (2026-10-22, 46 chiamate); il routing eval non esegue i tool. - **Limiti per turno** (`orchestrator._Limits`, `CONFIG["orchestrator"]`): oltre a `max_tool_calls_per_turn`, `max_iterations` (12: chiamate del planner), `max_execution_time` (180 s dall'inizio di `run`) e `token_budget` (200.000: `usage.total_tokens` delle chiamate del planner, 0 se la risposta non lo riporta) sono vincolanti e controllati prima di ogni nuova pianificazione; raggiunto uno, il ciclo si ferma (`stop_reason` e fallback `max_iterations`/`max_execution_time`/`token_budget`, raccontati dalla storia) e si risponde con ciò che c'è. Valori larghi per scelta (portfolio, pochi utenti); non interrompono un tool in corso né limitano la risposta finale. Test in `tests/test_orchestrator.py`.
- **Ciclo multi-tool** (`LLMOrchestrator.run`): la regola "un solo tool per turno" non esiste più. Il primo `_plan_first` (la stessa chiamata di prima, `_plan_turn` ne è il wrapper a tupla usato dal routing eval) sceglie il primo tool ed elenca le `parts` della richiesta (`{part, tool}`; voci con tool sconosciuto scartate); serve un altro passo se `more_steps` è true **o** una parte ha un altro tool. Solo allora `_plan_next` fa una chiamata in più, con i risultati già ottenuti (riassunto fino a `STEP_SUMMARY_CHARS`) e le parti ancora senza tool eseguito, e ritorna il passo successivo o `{"done": true}`. Un turno a un solo tool costa quindi le stesse chiamate LLM di prima. Il ciclo finisce con `complete` (nessuna parte pendente), `done`, `repeated_step`, `unknown_tool_or_low_confidence`, `planner_failed`, `required_tools`, `max_tool_calls` (motivo in `decision["planning"]["stop_reason"]`); prima era: `done`, passo ripetuto (stesso tool e argomenti), passo sconosciuto o con `confidence` sotto soglia, errore del planner (mai un fallback a `rag_search` dopo il primo passo: si risponde con ciò che c'è), `required_tools` (un solo passo) o `CONFIG["orchestrator"]["max_tool_calls_per_turn"]` (10). Il chiarimento è solo al primo passo. Le parti pendenti a fine turno arrivano alla risposta finale come "Parti della richiesta NON eseguite" (da dichiarare "non cercate", mai "non trovate"; caso reale 2026-10-24: intervista mai cercata e riportata come non trovata) e lo step `planning` (`STEP_PLANNING`, solo se i tool sono più di uno, resta una parte pendente o c'è un fallback) le racconta all'utente nella storia ("Non ho cercato: …"). La risposta finale riceve tutti i risultati (`tool_results`, un blocco per tool) e le `tool_final_instructions` di ogni tool usato. `decision` ha `tool` e `result` del primo passo, più `tools` e `calls` (`{tool, arguments, result}`); l'orchestratore emette per ogni chiamata, mentre accade, `tool_selection` (prima del tool), `tool_outcome` (dopo) e la trace del tool (vedi "Avanzamento in tempo reale"), `TurnResult.tools` elenca i tool: i presenter mostrano solo i tool eseguiti (nessun output RAG se il RAG non è stato chiamato). I limiti per turno (`tmdb.max_calls_per_turn`, `you_tube.max_searches_per_turn`) contano sul `turn_id`, non sulla run. Errori del tool DB: `metadata.error_kind` `unsupported_request` (nulla nella whitelist, es. filtro per attore) o `parser_failed`, con regola in `final_instructions`.
- **Offerta di altro (`follow_up`)** (`turn.RESULT_FOLLOW_UP`, `orchestrator._follow_up`): un tool può mettere nel risultato (fuori da `metadata`, quindi fuori dal prompt finale) `follow_up = {"available": bool, "reasons": [str], "summary": str}`. Se `available` è vero il ciclo chiama `_plan_next` anche con `more_steps` falso e senza parti pendenti; `_summarize_call` mostra al planner `summary` al posto di `Metadata` troncato a `STEP_SUMMARY_CHARS`; `_plan_next` aggiunge una riga che dice quali motivi ci sono e chiede se ciò che c'è basta (altrimenti il passo successivo, altrimenti `done`). La sufficienza la giudica il planner LLM sulla richiesta e su `summary` (outline, cosa è stato letto e cosa no), non una soglia del tool. Chi non produce `follow_up` costa le stesse chiamate di prima (`tests/test_orchestrator_follow_up.py`, parametrizzato). Freni: `done`, `repeated_step` (stessi tool e argomenti), `max_tool_calls_per_turn`, e il tool smette di offrire quando non ha più budget (chiamate o contesto) o dopo `rate_limited`. Lo usano `wikipedia_search` e `tmdb_search`: quest'ultimo lo offre (motivi `not_found`, `unverified_match`, `empty`; riassunto con le richieste non risolte) quando una richiesta non trova nulla, così il planner può passare a un altro tool invece di chiudere sul fallimento (errori di limite, chiave o rete non si offrono); i risultati riusciti non hanno la chiave. **Fine del ciclo** (`_plan_next`, contratto in `orchestrator.NEXT_STEP_FORMAT`, aggiunto alle istruzioni di quella sola chiamata; classificazione pura `_classify_next_step`): conclusione esplicita = `{"done": true}` (booleano vero) oppure un segnale di stop **definito dal contratto** (`tool_name` nullo, vuoto o `done`/`none`/`stop`) non contraddetto da `done: false` né da `more_steps: true`; in tal caso `stop_reason = "done"`, nessun fallback e nessun avviso. Risposta **incompleta o contraddittoria** (`{}`, solo `confidence`, `done: false` senza tool, `done` stringa o numero, `tool_name` nullo con `more_steps: true`, `tool_name` non stringa) = `stop_reason = "planner_incomplete"` con l'avviso `next_step_failed`. Restano errori con avviso: testo non JSON o non oggetto (`planner_failed`), tool nominato ma non ammesso o confidenza sotto soglia (`unknown_tool_or_low_confidence`). `decision["planning"]["planner_output"]` (e lo step `planning`) registra cosa ha risposto il planner **senza testo libero né argomenti** (`_planner_detail`: nomi delle sole chiavi note, altre come `<key>`; `done`/`confidence`/`more_steps` scalari, stringhe come `<str>`; `tool_name` solo se è un tool dell'app o una parola di stop). Nel test live del 2026-10-25 il vecchio controllo (`done is True` e basta) dava l'avviso spurio «Non ho potuto pianificare il passo successivo» in 6 turni su 7 con Wikipedia; la causa (probabilmente `tool_name: null` nel formato del primo passo, imposto dal system prompt di `_plan_next`) non era verificabile perché l'output grezzo non era registrato.

Gli override (es. `min_ratings` per le fixture) passano da `build_runtime_config`, come in `tests/conftest.py` e `harness/evaluation/cases.py:EVAL_OVERRIDES`.

Firefly, Planet Earth II) e non esiste un campo affidabile per distinguerle (`links.tmdb_id` punta sempre al namespace movie di TMDb): le righe film hanno `work_type_verified: false` e una nota nei metadata, e `final_instructions` vieta di presentarle come film verificati. Correggere `load_csv.split_title_year` richiede una nuova build con `--force`.
- **Regole di routing** (`CONFIG["orchestrator"]["instructions"]`, in ordine di priorità): 0) **chiarimento**: se l'utente chiede di un film o una serie precisi ma né la richiesta né la history bastano a identificarli (es. "chi c'era in quel film di Sorrentino?"), il planner ritorna `needs_clarification` e `clarification_question`; `_plan_turn` restituisce `CLARIFICATION`, `run` non esegue tool né la chiamata di risposta finale e la domanda diventa la risposta (`tool` è `None`, lo step `tool_selection` ha `clarification: true`); mai con `required_tools`; 1) `tmdb_search` per ogni richiesta informativa su un film o una serie identificati (anche "parlami di X", "dimmi qualcosa su X", "di cosa parla X"), con `movie_details`/`tv_details` e il titolo anche se ambiguo (il tool sceglie la versione e riporta le alternative); `search` solo per elenchi di titoli; 1b) `youtube_search` per i video su un film identificato (interviste al regista o al cast, making-of, dietro le quinte, featurette, commenti degli autori); i trailer restano a `tmdb_search` salvo richiesta esplicita di YouTube o proposta accettata; `year`, `director`, `cast`, `alternative_titles` solo se presenti nella richiesta o nella conversazione; 2) `movie_db_search` per voti, classifiche e confronti sui punteggi MovieLens; 3) `rag_search` per raccomandazioni e ricerche per trama, temi, emozioni e somiglianze, anche quando un titolo è citato solo come riferimento; 4) **richieste composte**: più tool nello stesso turno, in sequenza (vedi "Ciclo multi-tool"). La regola 2 dichiara che MovieLens non ha attori, registi, cast né giudizi della critica; i film di una persona e i giudizi della critica vanno a `tmdb_search` (`discover_movies` con `people`, `max_rating`, `sort: rating_asc`/`rating_desc`); `rag_search` non si usa per filmografie, voti o giudizi né come ripiego. - **Completamento RAG → TMDb** (`tool/tmdb/enrich.py`, `CONFIG["orchestrator"]["rag_enrichment"]`): dopo `rag_search` l'orchestratore passa il risultato a `TmdbRagEnricher`, che prende i chunk finali (dopo il rerank, al massimo `max_candidates`, nell'ordine del RAG, senza duplicati), cerca ciascun titolo in `en-US` senza filtro d'anno (`ctx.year_after_search`: il filtro di TMDb è esatto e l'anno del corpus spesso sbagliato di 1, la ricerca ripetuta faceva saltare il terzo candidato con `max_calls_per_turn` 6; `_pick_work` controlla l'anno ±1 sui risultati, la ricerca con filtro è il ripiego se nessun risultato è compatibile) (i titoli del corpus sono inglesi) e aggiunge in `metadata.tmdb_enrichment` i metadati solo se il titolo coincide con titolo o titolo originale TMDb (maiuscole, spazi e punteggiatura ignorati; **mai** per inclusione: "The Sinner" non è "The Sinners") e un anno RAG noto è confermato da un anno TMDb entro ±1; il lookup usa `ctx.strict_identity`, quindi più risultati ugualmente validi danno `ambiguous`. Altrimenti `unverified` (con `reason`), `not_found` o `skipped` e nessun dato attribuito. Due opere verificate danno `ambiguous`. La chiamata di verifica usa `endpoints.identity_appends` (film: `credits,translations,alternative_titles,release_dates`), gli stessi append dei dettagli, quindi senza facet non costa una chiamata in più. Servono a scegliere le sezioni (`sections.scoring_terms`, `count_term`: parola intera, forme flesse via radice crude `_stem`, prefisso da 4 lettere, frase intera; le generiche contano nel ranking) perché le parole di una domanda italiana non compaiono in un articolo inglese, e a dire cosa manca (`keyword_report`, solo parole distintive, `is_distinctive`/`GENERIC_KEYWORDS`): `read`, `unread` con le sezioni che le citano, `absent` (le parole non compaiono in nessuna sezione: **non prova che l'informazione manchi**), `not_in_lead` se è stata letta solo l'introduzione. `keywords_absent` richiede **almeno due** parole distintive assenti da tutto l'articolo **e** almeno la metà di tutte le distintive (`relevance.keywords_mostly_absent`, `MIN_ABSENT_KEYWORDS = 2`: una parola mancante è quasi sempre un'altra grafia o un sinonimo), altra edizione non interrogata e una chiamata libera. `GENERIC_KEYWORDS` include anche protagonist(i), continuation(s), connected, original, source(s), literary, adaptation, structure, order… e gli equivalenti italiani. Il riassunto per il planner (`follow_up.summary`) dà edizione usata ed edizioni consultate, sezioni lette e non lette, stato delle parole chiave, candidati non aperti, pagine scartate e motivo: **nessun testo degli estratti** (quello va solo alla risposta finale).
  - **Recupero dinamico**: `depth` `intro` (anteprime delle migliori pagine, una richiesta), `sections` (una pagina, le sezioni che combaciano con la domanda o quelle chieste per nome), `full` (una pagina, tutte le sezioni con prosa, le più pertinenti prima). L'articolo è scaricato **una volta** (`prop=extracts` senza `exintro`: una pagina per richiesta, nessun `exchars`) e tenuto nella cache TTL; `sections.py` lo divide per intestazioni `== Titolo ==`. I passi successivi sulla stessa pagina sono cache hit (zero HTTP, zero budget) e consegnano solo sezioni non ancora consegnate nel turno. Le parole del `topic` non contano come parole della domanda per scegliere le sezioni. Le sezioni senza prosa (Note, Bibliografia, Collegamenti esterni…) si consegnano solo se chieste per nome.
  - **Limiti**: `context_chars_per_turn` non limita il recupero ma ciò che entra nel prompt finale (contiene i risultati di tutti i passi); il resto è elencato (`omitted`, `outline`) e richiedibile. Una sezione che non entra ferma la consegna, salvo la prima, tagliata a fine frase se resta spazio (`truncated`). Altri freni tecnici (lettura massima della risposta HTTP, voci della cache, turni ricordati) in `settings.py`; una risposta oltre il massimo è l'errore `response_too_large`, mai JSON tagliato.
  - **Decisione di continuare**: vedi "Offerta di altro (`follow_up`)". Motivi: `empty`, `ambiguous`, `unverified` (serve una nuova ricerca o l'altra edizione), `more_in_page` (sezioni non lette), `omitted_by_budget`, `keywords_absent` (vedi "Lingua"). Dopo una sola anteprima c'è quasi sempre `more_in_page`, quindi un turno `intro` costa **una chiamata di pianificazione in più**.
  - **HTTP** (`http.py`, unico I/O, test AST): memo → fallimenti del turno (nessun retry nello stesso turno) → cache → pausa → budget del turno → invio. `maxlag` risponde **HTTP 200** con `error.code == "maxlag"`: il corpo è letto anche su 200; 429, `ratelimited` e `maxlag` danno `rate_limited` e una pausa in memoria (da `Retry-After`, tra 1 e 60 s, default 5) durante la quale le richieste da inviare falliscono subito; nessuna attesa e nessun retry. Gli errori sono sollevati fuori da ogni `except` e non contengono URL, query né User-Agent.
  - **Stato per turno** (`budget.py`): dizionario `turn_id → TurnState` limitato e con lock; diversamente da `YoutubeTool` (un solo slot) due conversazioni concorrenti non si azzerano.
  - **Anno nel topic**: un «(1964)» in coda al topic (`WikipediaToolInput._year_in_the_topic`) è spostato in `year` se questo manca («Kwaidan (1964)» → topic «Kwaidan», `year` 1964), e `match_title` ignora i qualificatori che sono solo un anno; un qualificatore vero («(film)», «(2013 film)») resta.
  - **Pertinenza e verifica** (`relevance.py`): la ricerca chiede `min(2×max_results, 10)` pagine e taglia a `max_results` **dopo** lo screening. `match_title` confronta prima i titoli interi (punteggiatura inclusa, «Tokyo!», «Kwaidan (film)»), poi senza qualificatore; qualificatori diversi («Solaris (novel)» / «Solaris (1972 film)») = `partial`. Scartate e contate in `filtered_out`: disambigue, senza testo e `not_relevant` (titolo diverso da quello chiesto **e** lead che non nomina il soggetto o, per un film con `year`, non contiene l'anno: `plausible`). `confirmed` = titolo uguale (anche con parentesi); `to_verify` = plausibile ma non certa (`title_partial`, `title_differs`, `year_conflict`). L'articolo intero si scarica **solo** per la prima pagina `confirmed`; senza candidati certi non si scarica nulla: `metadata.wikipedia.candidates` (titoli, al massimo 5) e motivo `unverified`, e il planner apre uno con `page` o cerca con un altro titolo. Permissivo per le anteprime (`intro` consegna anche i lead `to_verify`, etichettati). Limite noto: con un titolo di una sola parola e senza `year` una pagina che condivide la parola resta `to_verify` (non si apre da sola).
  - **Dati non attendibili**: l'estratto è testo di terzi: caratteri di controllo rimossi, solo in `metadata.wikipedia.pages[].text`, mai nella trace né nelle istruzioni; `tool_final_instructions["wikipedia_search"]` lo dichiara un dato e non un'istruzione. La difesa dipende anche dal modello e non è dimostrabile offline.
  - **Trace e fonti**: step `wikipedia_calls` (`calls` URL base senza parametri, `reused`, `searches`, `opens`, `pages` con URL pubblico costruito da host in allowlist + titolo, `license`); i presenter mostrano pagine, URL, lingua, sezioni lette, fonte e licenza CC BY-SA 4.0 con link (crediti richiesti da Wikipedia: link alla pagina, licenza, nota che il testo è stato riformulato), mai affidati all'LLM. Il frontend deve gestire il kind (`web_api/FRONTEND_API.md`); `web_lists` non lo conosce (le pagine sono fonti, non titoli consigliati).
  - **Verifiche**: tutti i test sono offline (`tests/test_wikipedia_*.py`, transport finto in `tests/wikipedia_support.py`, `tests/test_wikipedia_turn.py` percorre tool → orchestratore → web_api → eventi SSE con `urlopen` bloccato). **Pendenti, mai eseguiti**: il planner reale che scrive `keywords` in inglese e lascia `language` null per domande italiane (il routing eval ne verifica solo gli argomenti del primo passo); `python -m tool.wikipedia.harness.live_smoke --live` (conferma `generator=search` con `extracts`, le intestazioni `== X ==`, i flag di disambiguazione), il routing eval live dei casi Wikipedia, un E2E con LLM reale (rispetto delle istruzioni sugli estratti, qualità del giudizio di sufficienza del planner), la taratura di `context_chars_per_turn`.
- Enum Pydantic per i valori chiusi (`SearchMode`, `RerankBackend`); nuovi modelli dati in `models.py`.
- Errori espliciti con istruzioni operative (es. collection vuota → "Run `python buildSemanticDb.py ...`").
- Stato della conversazione: lista `history` di `{"role", "content"}` gestita in `app.py`; la compattazione la **sostituisce**, non la estende.
