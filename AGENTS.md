# AGENTS.md — NetflixScout

## Avvio dei servizi (due terminali, dalla radice del repository)
```bash
./scripts/start_qdrant.sh                                                              # terminale 1: server Qdrant 1.20.0 su 127.0.0.1:6333
source .venv/bin/activate && uvicorn web_api.main:app --host 127.0.0.1 --port 8000     # terminale 2: backend API per il frontend (un solo worker)
```
Qdrant va acceso prima. Lo script cerca il binario in `$QDRANT_BIN`, poi `bin/qdrant` (non versionato), poi nel `PATH`; se manca lo dice e indica dove metterlo
(release ufficiale 1.20.0). Pronto: `curl http://127.0.0.1:6333/collections` elenca `netflix_scout`; il backend risponde `{"status":"ok"}` su `/health`. Per la chat da terminale: `python app.py`.

## 1. Contesto del Progetto

**Scopo**: assistente conversazionale da terminale che consiglia film usando RAG sul CMU Movie Summary Corpus, un DB SQL locale read-only di MovieLens 32M (voti, classifiche, generi per anno, tag), l'API TMDb (dati aggiornati: cast, uscite, streaming, serie, persone, trending), l'API OMDb (punteggi IMDb, Metascore, Rotten Tomatoes di un titolo identificato) e la YouTube Data API v3 (video su un film identificato: interviste a regista e cast, making-of, dietro le quinte, commenti degli autori). Risponde solo a domande cinematografiche (classificatore anti off-topic e anti jailbreak).

**Stack**
- Python 3.11 (`.venv/` locale), nessun `pyproject.toml`: le dipendenze stanno in `requirements.txt` (versioni pinnate).
- LLM ed embedding: `openai` (Responses API + Chat Completions per il classificatore; embedding `text-embedding-3-small`).
- Vector store: **solo Qdrant** (`qdrant-client` 1.20.0 fissato insieme alla versione del server in `store/settings.py`), collezione `netflix_scout` (42.522 punti, 1536 dimensioni, cosine) nello storage del server `dbVettoriale/qdrant_openai/storage`. Modalità `server` (predefinita, `http://127.0.0.1:6333`) | `embedded` | `memory` (solo test), da `CONFIG["rag"]["vectorstore"]["qdrant"]` o dalle variabili `VECTORSTORE_QDRANT_MODE|URL|PATH` (`QDRANT_API_KEY` solo per un server con chiave). Non esiste più nessun altro motore: ChromaDB, `VECTORSTORE_ENGINE` e ogni ritorno a Chroma sono stati rimossi (la vecchia cartella `dbVettoriale/openai`, se presente, è un dato inutilizzato che si può cancellare a mano). Storia, parità, ricostruzione e prove: `docs/qdrant_migration/README.md`.
- Retrieval: semantico, BM25 (`rank-bm25`), ibrido con RRF.
- DB MovieLens: `sqlite3` della stdlib; CSV e DB in `movie_db/data/` (ignorata da git, read-only a runtime).
- Rerank: `cohere` (`rerank-v3.5`) oppure LLM.
- TMDb: `urllib.request` della stdlib (nessuna dipendenza nuova), chiave da `.env` (`VUE_APP_TMDB_API_KEY`, `VUE_APP_TMDB_BASE_URL`).
- YouTube: `urllib.request` e `zoneinfo` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), chiave `YOUTUBE_API_KEY` da `.env`, letta solo da `tool/youtube/auth.py`.
- Wikipedia: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API pubblica MediaWiki), User-Agent con repository e contatto in `tool/wikipedia/settings.py` (policy Wikimedia).
- OMDb: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), chiave `OMDB_API_KEY` da `.env`, letta solo da `tool/omdb/auth.py`. Termini: uso personale e non commerciale (contenuto CC BY-NC 4.0; vietati indici e ridistribuzione), vedi «Tool OMDb».
- TVmaze: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API pubblica `https://api.tvmaze.com`), User-Agent con repository e contatto in `tool/tvmaze/settings.py`; dati CC BY-SA, attribuzione con link (vedi «Tool TVmaze», dubbi legali ancora aperti).
- Wikidata: `urllib.request` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), **nessuna chiave** (API MediaWiki di ricerca delle entità e Wikidata Query Service, SPARQL), User-Agent con repository e contatto in `tool/wikidata/settings.py`; dati CC0 (vedi «Tool Wikidata»).
- Modelli dati: `pydantic` v2. Loader: `pypdf`, `python-docx`, `beautifulsoup4`, `markdown-it-py`.
- Test: `pytest`. Nessun linter o formatter configurato.

**Flusso a runtime** (`app.py`)
```
input + ultimi classifier_context_messages della history → classify_query_domain (gpt-4o-mini, JSON) ──non cinema──→ rifiuto secco (`block_reply` dello stesso classificatore, nella lingua dell'ultimo messaggio; ripiego fisso it/en/de, altrimenti inglese), senza stadio, storia né riquadro
                         │ cinema
                         ▼
LLMOrchestrator (orchestrator.py) → sceglie il tool → RagTool.run → run_rag (retrieve + rerank, nessuna generazione) → TmdbRagEnricher (metadati TMDb dei candidati)
                                                   oppure MovieDbTool.run → parser LLM → MovieDbQuery → SQL whitelistato read-only
                                                   oppure TmdbTool.run → TmdbToolInput validato → risoluzione ID → endpoint fissi (budget per turno) → contesto limitato
                                                   oppure YoutubeTool.run → YoutubeToolInput validato → search.list per categoria (limite per turno) → un videos.list → filtro di pertinenza → metadata + trace
                                                   oppure OmdbTool.run → OmdbToolInput validato → (ricerca per titolo) → identificazione certa → record per IMDb ID → punteggi con stato (budget per turno, nessuna cache) → metadata + trace
                                                   oppure WikipediaTool.run → WikipediaToolInput validato → ricerca (anteprime) o articolo intero scaricato una volta (cache) → sezioni consegnate fino al budget di contesto del turno → metadata + trace + `follow_up` (cosa è stato letto e cosa no)
                                                   oppure WikidataTool.run → WikidataToolInput validato → (ricerca entità per titolo) → identificazione certa (anno, regista, ID IMDb/TMDb) → relazioni dichiarate con query SPARQL predefinite (budget per turno, nessuna cache) → metadata + trace + `follow_up`
                         ▼
il planner può concatenare altri tool nello stesso turno (fino a max_tool_calls_per_turn, ogni passo usa i dati dei precedenti) → l'orchestratore genera la risposta finale (final_instructions + tool_final_instructions di ogni tool usato) → history → compattazione oltre memory_window_size

Ogni step (query riscritta, tool scelto, esito e secondi, trace del tool, fallback) va al TurnObserver del canale MENTRE accade; il terminale lo stampa subito (storia in poche frasi + blocco del tool), il web riceve gli stessi dati in JSON. La risposta finale è UNA chiamata in streaming: il testo arriva all'osservatore con `answer_delta` mentre il modello scrive (anche il messaggio di blocco, il chiarimento e il ripiego arrivano come delta); alla fine present(..., streamed=True) chiude solo la riga e dà l'avviso di compattazione.
```

## 3. Linee Guida di Stile e Architettura

**Formattazione**
- PEP 8, indentazione di 4 spazi, righe di circa 100 caratteri, virgole finali nelle chiamate su più righe.
- `from __future__ import annotations` in testa ai moduli nuovi; type hint moderni (`list[dict]`, `str | None`).
- Import relativi dentro `tool/rag/FromQueryEmbeddingToRes/` (`from .models import ...`), assoluti dalla root (`from tool.rag.FromQueryEmbeddingToRes... import ...`).
- Le funzioni private del modulo hanno il prefisso `_`; argomenti keyword-only (`*`) per le API pubbliche (`run_rag`, `Tool.run`).
- Naming misto italiano/inglese **già esistente** (`recupera`, `genera`, `apri_collection`, `indicizza`, `testo`, `k_largo`, `k_finale`): rispetta il nome già usato nel modulo che tocchi, non rinominare.
- Prompt e messaggi per l'utente finale in italiano, docstring ed errori tecnici in inglese.

**Pattern architetturali**
- **Parametri RAG scelti dal planner**: `k_finale` (quanti film chiede l'utente; null = default di `CONFIG["rag"]["retrieval"]`, con `limits.k_finale` min/max). e `search_mode` (null = `semantic`; `hybrid` solo se la richiesta si regge su parole concrete che devono comparire nella trama: personaggio, luogo, oggetto, termine raro, frase tra virgolette; `bm25` da solo non è ammesso e `resolve_retrieval` lo ignora; in hybrid la parte keyword cerca con la `semantic_query` inglese, non con le parole dell'utente, perché il corpus è inglese). `RagToolInput` li espone (`extra="forbid"`); `RagTool.run` li passa a `retrieval_params.resolve_retrieval`, che clampa `k_finale`, tiene `k_finale <= k_largo <= fetch_k`, ignora valori non validi e ogni altra chiave, e lavora su una copia della config. Lo step `retrieval` riporta `retrieval_params` (`effective`, `overridden`). `k_largo`, `fetch_k` e `genre_boost` sono stati provati nello schema del planner (insieme a `search_mode`) e **rimossi**: due A/B live del 2026-10-24 (10 domande, default contro planner) non hanno mostrato alcun beneficio oltre al conteggio (nei casi in cui differivano solo quelli, 3 su 3 uguali; commedie giapponesi anni 50: più violazioni dei vincoli per film; il planner scriveva `genre_boost` anche fuori scala, 1,5–2,0). Il guadagno netto è `k_finale` uguale al numero chiesto (7 migliori, 0 peggiori, 3 uguali nel secondo run; limite: la metrica premia il conteggio corretto, quindi è una prova sul numero di film, non sulla qualità dei titoli). `search_mode` è stato reintrodotto il 2026-10-26 limitato a `semantic`/`hybrid`: e2e reale su 2 domande (personaggio nominato → hybrid, trovato *Hannibal*; tema → semantic); il beneficio di qualità non è misurato con un A/B. Caso di routing in `routing_cases.py`. Valutazione: `routing_cases.py` (`expected_rag`) e `python -m movie_db.harness.evaluation.run_rag_params_eval --live` (A/B, ~10 planner + 20 parser + 20 Cohere, pause di 7 s). Correzione collaterale: `bm25`/`hybrid` leggono la collection a pagine e tengono l'indice in cache (`hybrid.py`; prima `collection.get()` falliva con "too many SQL variables" su 42k chunk).
- **Catalogo TMDb → Qdrant** (`CONFIG["catalog"]["enabled"]`, **False**; piano e decisioni in `docs/qdrant_migration/catalog/`): un film citato dall'utente e assente dall'indice, verificato da `tmdb_search` (`movie_details` riuscito, identità certa), viene letto in `en-US` (`film_record.py`, mai `localized()`), incorporato con `text-embedding-3-small` (testo = solo la trama inglese, almeno 100 caratteri, altrimenti scarto) e salvato come punto `tmdb:movie:<id>` (`source="tmdb"`). Un film già nel corpus CMU (stesso titolo e anno; regole in `store/catalog.py:decide_link`) non è duplicato: si scrive solo `tmdb_id` sul punto CMU, mai documento o vettore. Ogni scrittura su un punto TMDb è un confronto condizionale sulla `version`; il ponte `catalog_enricher.py` (registrato su `tmdb_search` da `app.build_catalog_enricher` solo se acceso, con Qdrant `embedded` o `server`) non solleva mai e scrive l'esito solo in `tmdb_calls.data.catalog`. Dopo una scrittura la cache BM25 si invalida (`hybrid.invalidate_bm25`). **Stato**: logica e integrazione provate offline; atomicità sul server provata con `tests/qdrant_catalog_race.py` (vedi `docs/qdrant_migration/catalog/race_report.md`); la calibrazione C (embedding reali) e l'attivazione NON sono eseguite e richiedono l'autorizzazione del proprietario. I punti TMDb non sono ricostruibili dal dataset: prima di accendere, copia verificata dello storage Qdrant.
- **"Simile a X, diverso da Y"** (`CONFIG["rag"]["signals"]["avoid_query"]`, `rerank.avoid_llm`, `rerank.avoid_pool`; misura e limiti in `docs/qdrant_migration/rerank_avoid_report.md`): il parser separa ciò che si vuole evitare in `QuerySignals.avoid_query` (l'embedding contiene solo il voluto); se c'è, il pool candidato sale a 50 e li ordina `rerank_llm_request` (LLM che conosce i film citati; ricade su Cohere in caso di errore; trame senza titolo escluse). Misurato su 40 domande: film buoni 0,44 → 0,78 (pool 50), prova end-to-end 0,45 → 0,72; distanza dal secondo film non migliorata; la fusione Cohere "voluto − da evitare" non ha dato beneficio ed è stata rimossa.
- **Film di riferimento con vettore reale** (`rag.reference` — `enabled` **True**, strategia `best_score` — e `rag.signals.reference_titles` **True**; misura e prove in `docs/qdrant_migration/reference_embeddings_report.md`): il parser estrae `like_titles`/`avoid_titles` (titolo + anno solo se certo); `reference_flow.py` ne trova il vettore nell'indice (riuso, zero chiamate esterne), oppure legge la trama inglese su TMDb (`film_record.read_film`, identità verificata, mai un omonimo pari), la incorpora una volta e la salva come punto persistente `tmdb:movie:<id>` (o la collega al punto del corpus della stessa opera: nessun duplicato); una ripetizione non costa nulla. Trama assente o corta → `no_plot`, nessun embedding; errori TMDb/embedding → `unavailable`, la ricerca prosegue come prima. **La ricerca è guidata (`search(references=)`) solo se almeno un riferimento POSITIVO è risolto**; con un solo negativo si esegue la ricerca normale (un negativo da solo peggiorava i risultati, misurato). I film citati sono esclusi per id. Tracce in `retrieval.data.references`; `tmdb.max_calls_per_turn` è 10 per questo. Misurato (40 domande, un giudice LLM): qualità non distinguibile dal controllo, film citato restituito 5 → 0; non è dimostrato un miglioramento della somiglianza né della distanza. Scrive nella collezione reale (punti `tmdb:`) quando un utente cita un film assente.
- **Impostazioni utente (`preferences/`)**: sei campi (spoiler, lunghezza, tono, approccio, tipo di contenuto, fonti preferite), applicati **per turno** e solo dal web. Regole decise: (1) **nessuna impostazione aggiunge chiamate, con UNA eccezione dichiarata** (decisione del proprietario, 2026-10-27): le impostazioni orientano la scelta tra tool già adatti (planner, solo tipo di contenuto e fonti) e la forma della risposta, ma la fonte `interviews`, per un film o una serie identificati da un titolo (non per classifiche, raccomandazioni senza titolo, domande statistiche o di sola trama), fa aggiungere al planner un passo `youtube_search` (`kinds` director_interview e cast_interview, `more_steps` true), così i video compaiono nel testo e nell'evento `lists`; costa fino a `max_searches_per_turn` (2) ricerche YouTube, sulla quota di 100 al giorno; non toccano `k_finale` né altri parametri di ricerca, e non prevalgono mai sull'intento esplicito né sulle regole numerate di routing; (2) **spoiler disattivati e richiesta esplicita di uno spoiler**: lo spoiler non si rivela mai e la risposta dice che la richiesta contraddice l'impostazione; (3) **il tono non si applica ai messaggi fissi** (chiarimento, blocco non-cinema, ripiego: nessuna chiamata in più); (4) il terminale usa sempre il comportamento di prima (`preferences=None`); (5) il cliente non riceve mai le istruzioni interne. I due «Rispondi in modo conciso.» di `tool_final_instructions` sono stati tolti (contraddicevano `in-depth`) e `final_instructions` non impone più l'ordine dei film RAG né il livello di dettaglio della scheda: lo decide la lunghezza scelta. Le istruzioni delle impostazioni stanno in `preferences/behavior.py` e non in `CONFIG` (motivo: separazione pubblico/privato e dimensione di `app.py`). **Risposta senza provenienza e `short` vera** (2026-10-27, richiesta del proprietario): il testo finale non dice mai da quale tool, API, database o pagina vengono i dati (lo fanno i presenter), solo il tipo di dato quando cambia il senso (voto del pubblico, non della critica); `short` prevale su ogni istruzione di completezza (titolo, anno, una riga) e con l'approccio «confronto» il confronto resta, compatto. Non verificato con un LLM reale. **Default** (in `fields.json`): spoiler `false`, lunghezza `medium` (scelta del proprietario il 2026-10-27, non `in-depth`), tono `technician`, approccio `alternatives comparison`, contenuto `both`, fonti `official information`. **Verifica reale del 2026-10-27** (10 turni con LLM, TMDb, Wikipedia, MovieLens e Qdrant reali, passando da `handle_query` come il web, nessuna chiamata YouTube): spoiler spento + richiesta del finale → nessun finale e avviso di contraddizione; spoiler acceso → finale con indicazione della pagina; `short` 563 caratteri contro `in-depth` 751 sulla stessa domanda (la differenza è piccola perché i dati ricevuti sono pochi: la lunghezza non inventa contenuto); `Homie` con consiglio diretto → un solo film, slang e una volgarità, dati intatti; `technician` con confronto → tre alternative e scelta finale; fonti `reviews` → facet `reviews` aggiunta alla **stessa** richiesta TMDb, risposta che dice che non è critica professionale; fonti `user ratings` → `movie_db_search` con la fonte dichiarata; fonti `interviews` su una domanda di dati ufficiali → solo `tmdb_search`, nessun video (la preferenza non vince sull'intento e non aggiunge chiamate). **Difetto trovato e risolto** (stesso giorno, confermato con `GET /genre/tv/list` reale): con `content_type: series` il planner sceglieva `discover_tv`, ma TMDb non ha «Thriller» tra i generi delle serie, quindi `reference.genre_ids` dava `unresolved_filter`, che non offriva `follow_up` e chiudeva il turno. Ora `TV_GENRE_ALIASES` (`tool/tmdb/operations/reference.py`: thriller→Mystery, science fiction→Sci-Fi & Fantasy, solo per le serie) lo risolve, e un genere senza equivalente (es. Horror per le serie) offre il `follow_up` con l'indicazione di controllare i nomi con l'operazione `genres` (`UNRESOLVED_ERRORS` e `FILTER_NAME_HINT` in `tool/tmdb/tool.py`). Test: `tests/test_tmdb_tv_genres.py`. Campione di 10 turni e una sola esecuzione. Limiti: gli spoiler sono una richiesta al modello, non un filtro sui dati (trame RAG, sezioni *Plot* di Wikipedia, recensioni e titoli YouTube arrivano al modello interi); non sono stati provati con un LLM reale il rispetto di `Homie` su più turni né il routing eval completo con le preferenze (`run_routing_eval --live`, con permesso).
- **Config-driven**: tutti i parametri (modelli, k, backend, prompt) vivono in `CONFIG` in `app.py`. Niente valori hardcoded nei moduli: passa `config` come dict. Gli override passano da `build_runtime_config(overrides)`.
- `_resolve_runtime_config` normalizza la config RAG (modello di embedding iniettato nella config Qdrant, default della conversazione): chiamala prima di accedere a vectorstore ed embedding.
- **Contratto dei tool**: ogni tool rispetta il `Tool` Protocol (`name`, `description`, `input_schema`, `run(*, query, params, conversation_history) -> dict`). `input_schema` deriva da un modello Pydantic (`model_json_schema()`). Un nuovo tool vive in `tool/<nome>/` (mai nella root), con import relativi e senza importare altri tool, presenter o canali (`tests/test_tool_package.py`), e si registra in `build_app` e in `CONFIG["orchestrator"]["allowed_tools"]`, senza toccare il core.
- **Separazione dei ruoli**: `RagTool`/`run_rag` restituiscono solo evidenza strutturata (`chunks` + `metadata` + `trace`); la risposta finale la genera solo l'orchestratore.
- **Avanzamento in tempo reale**: il turno è sincrono, quindi senza osservatore l'utente non vede nulla finché `LLMOrchestrator.run` non ritorna (era la causa del terminale muto). `handle_query(..., observer=)` e `run(..., observer=)` accettano un `TurnObserver` (`turn.py`: `step(TraceStep)` e `status(stage)`): l'orchestratore emette gli step **mentre accadono** (`query_rewrite`, per ogni tool `tool_selection` con `purpose` e `arguments` **prima** della chiamata, poi `tool_outcome` con `elapsed_ms`/`status`/`reason` e la trace del tool, `planning` per ultimo) e `status(answering)` prima della risposta finale; un osservatore che solleva non rompe il turno. `TurnResult.steps` e `TurnResult.story` sono gli stessi che vede l'osservatore (`_TurnRecorder` in `app.py`); un orchestratore finto nei test deve emettere gli step (`tests/turn_support.py:stream_decision`). Ogni tool mette in `result["outcome"]` (`turn.tool_outcome`: `ok|empty|error` + `reason`, fuori da `metadata`) l'esito che la storia racconta; senza `outcome` conta la presenza di `chunks`. I fallback silenziosi (`planner_failed`, `low_confidence`, `unknown_tool`, `next_step_failed`, `max_tool_calls`, `answer_failed`) stanno in `decision["planning"]["fallbacks"]` e la storia li dice solo quando accadono.
- **Terminale e web uniformi**: stesso contenuto, formato diverso. Ogni step ha una vista in `presenters/*_view.py` (testi it/en, dati) e i due canali ne cambiano solo la forma; la storia (`story_view.StoryBuilder`) è un'unica sequenza di `StoryLine(level, text, tool)` (il terminale aggiunge l'emoji per `level`, il web lascia l'icona al frontend; dopo `MAX_OK_LINES` esiti positivi restano solo i problemi). Gli step di flusso (`classification`, `query_rewrite`, `tool_selection`, `tool_outcome`, `planning`) sono raccontati dalla storia e non hanno renderer né serializer; ogni altro kind deve stare sia in `STEP_RENDERERS` sia in `STEP_SERIALIZERS` (`tests/test_presenter_parity.py`). Un nuovo tool aggiunge la vista condivisa, il renderer terminale e il serializer web.
- **Risposta finale in streaming** (`LLMOrchestrator._generate_final_answer`): sempre `responses.create(stream=True)`, una sola chiamata, mai una seconda. Gli eventi dell'SDK (`response.output_text.delta`, `completed`, `incomplete`, `failed`, `error`, refusal) sono letti in `_consume_stream`; il testo va a `observer.answer_delta`. Senza `final_output` (terminale) i delta sono il testo; con `final_output` (web) i delta grezzi sono JSON e passano da `AnswerFieldStream` (nome del campo da `final_output["answer_field"]`), quindi il canale vede solo il testo di `answer` già decodificato. `answer` e `lists` autorevoli vengono dal parse del JSON completo; lo schema strict ha `answer` PRIMA di `lists` (test) per lo streaming progressivo, ma l'ordine reale del modello non è dimostrato offline (`live_stream_check`). Se lo stream fallisce (incomplete/failed/errore/refusal/JSON non valido): dopo alcuni delta la risposta è il testo già mostrato (`lists: []`), senza delta il ripiego esistente (anch'esso emesso come delta), in entrambi i casi fallback `answer_failed`; la cronologia contiene ciò che l'utente ha visto. Lo step `planning` esce PRIMA della risposta (parti non cercate prima del testo); solo `answer_failed` ne produce un secondo, minimo. `handle_query` tiene la history intera se la compattazione fallisce. Terminale: `TerminalObserver.answer_delta` stampa il riquadro al primo testo non bianco e poi i pezzi; `render(streamed=True)` non ristampa la risposta. Web: il frontend concatena i `answer_delta`; `answer_end.replace` è null se `streamed.strip() == final.strip()`, altrimenti la risposta intera strippata.
- **Server HTTP/SSE (`web_api/`)**: il turno è sincrono e invariato; gira in `asyncio.to_thread` in una task INDIPENDENTE dal client. Commit della history (`finish_turn`, unico punto) quando `handle_query` ritorna, anche se il client è sparito; eccezione → history invariata; la conversazione resta `busy` fino alla fine reale del lavoro (409 nel frattempo); nessuna cancellazione del turno; alla disconnessione la sottoscrizione si chiude e gli eventi successivi sono scartati (la coda non cresce). Nessuna autenticazione né rate limit, per scelta (portfolio, budget limitato sulla chiave backend). Un solo worker.
- **Il nucleo non stampa**: `handle_query` produce un `TurnResult` con gli step (`trace` dei tool inclusa). L'output sta solo in `presenters/<canale>/<tool>/` (`rag`, `db`, `api`); fuori dalle cartelle dei tool solo il collante del flusso e le viste condivise; un nuovo tool aggiunge `presenters/terminal/<tool>/` e `presenters/web/<tool>/` (struttura verificata da `tests/test_tmdb_presenters.py`). Il canale (`OutputChannel`) lo dichiara l'entry point: `python app.py` → `terminal`, la futura route FastAPI → `web`. Niente `print` fuori da `presenters/terminal/` (eccezioni: builder offline, loop legacy in `chat.py`).
- **Query autonoma per i follow-up**: nella stessa chiamata LLM con cui sceglie il tool, l'orchestratore (`_plan_turn`) riscrive la domanda in modo autonomo usando la history (`standalone_query`) e la passa a **qualunque** tool, anche con `required_tools` o fallback. Senza history o se l'LLM fallisce si usa la domanda originale. Per `rag_search` la ricerca parte sempre dalla `standalone_query` (le parole dell'utente); `arguments.query` del planner arriva al parser dei segnali solo come `query_hint` ("Planner rewrite"), perché può essere vaga (caso reale: "Film simili a Mare dentro, che affrontino temi e atmosfere analoghi"); il trace `retrieval` riporta entrambe. La history va passata **intera e invariata** (niente finestre scorrevoli): un prefisso stabile permette al prompt caching del provider di riusarla.
- **Lingua del turno** (decisione del 2026-10-27; `turn.py`: `normalize_language`, `label_language`, `language_name`): fa fede **solo l'ultimo messaggio** dell'utente, mai la lingua prevalente né la history (che serve solo ai riferimenti): si può cambiare lingua al messaggio 10 e la risposta 11 segue. Il classificatore restituisce `language` (codice ISO 639-1, al posto di `is_italian`; `query_language` non esiste più); `_validate_classification` lo normalizza (`de-DE`→`de`, «German»→`de`) e un valore non valido o assente non solleva: `resolve_language` ripiega sui marcatori it/en e poi su `en`. `detect_language_markers` (parole funzionali it/en) corregge il modello **solo** quando questo ha detto it/en o nulla, mai su una lingua terza (una frase tedesca attorno a un titolo italiano resta tedesca). Un messaggio senza contenuto linguistico (solo un titolo) segue, per istruzione al modello, l'ultimo messaggio utente precedente: unico caso in cui la history conta, non dimostrabile offline. `TurnResult.language` e `answer_end.language` sono una stringa libera. **Testi fissi** (storia, etichette degli step, titoli RAG, blocchi del terminale, ripiego del blocco e `NO_ANSWER_TEXTS`) esistono in it/en/de; ogni altra lingua legge l'inglese (`label_language`) mentre il testo libero è scritto dal modello nella lingua giusta. Aggiungere una lingua = una colonna in ogni tabella (`presenters/*_view.py`, `presenters/terminal/texts.py`, `orchestrator.NO_ANSWER_TEXTS`, `app.NON_CINEMA_BLOCK_MESSAGES`; `tests/test_turn_language.py` verifica che le colonne siano complete). **Prompt**: `run(answer_language=)` aggiunge UNA riga dinamica alla risposta finale (dopo le regole dei tool e prima delle impostazioni utente, che governano ancora la forma) e una al planner (lingua della domanda di chiarimento); senza lingua i prompt sono identici a prima. Banner, prompt `Tu >` e saluto del terminale non appartengono a un messaggio e restano italiani. Specifica per il front-end: `docs/frontend_handoff_language.md`.
- **Contesto del classificatore**: `handle_query` passa a `classify_query_domain(query, history)` gli ultimi `CONFIG["orchestrator"]["classifier_context_messages"]` messaggi della history. Il guardrail gira prima della riscrittura `standalone_query`: senza contesto un follow-up come "ne puoi trovare 3 più recenti?" verrebbe bloccato. La history serve solo a risolvere riferimenti impliciti; si classifica sempre l'ultima query. Il prompt considera cinematografiche anche le richieste su un film già citato (trama, dettagli, traduzione) in qualsiasi lingua: chiedere la risposta in un'altra lingua non è un jailbreak (prima "Could you get in english the plot from the movie you just advised?" veniva bloccata). Lo step `classification` resta nel trace ma non viene stampato (né a terminale né sul web): un blocco mostra solo il messaggio di blocco. **Lingua**: vedi «Lingua del turno» qui sotto.
- **Trace dei tool**: ogni tool restituisce `"trace": [{kind, title, data}]` fuori da `metadata` (che finisce nel prompt). Un `kind` nuovo ha il renderer nella cartella del suo tool (`presenters/terminal/<tool>/renderer.py`, su una vista condivisa) e va registrato in `presenters/terminal/renderer.py:STEP_RENDERERS` (firma `(step, language)`, `language` = `TurnResult.language`) **e** il serializer in `presenters/web/payload.py:STEP_SERIALIZERS`, altrimenti viene stampato col fallback generico.
- **Testo dell'embedding**: il corpus è composto da trame in inglese. Il parser `_extract_query_signals` (`retrieval.py`) produce `QuerySignals` in inglese con `semantic_query` (la frase su cui si fa l'embedding) e `genres` (vocabolario del corpus). `vectorstore.search` fa l'embedding di `semantic_query`, altrimenti della query originale, **mai** del join dei `positive_signals`: un insieme di keyword italiane faceva finire il retrieval su film italiani o storici. Il genere non viene indicizzato nel testo: entra nel ranking con il boost `retrieval.genre_boost` sul pool di `retrieval.fetch_k` e nel documento passato al reranker (`rerank._documento_per_rerank`). Lo step `retrieval` del trace riporta `embedded_text` e `signals`. Il reranker riceve `compose_rerank_query`: `semantic_query` (altrimenti la query) più "Must match: …" con i segnali positivi e i generi richiesti le cui parole chiave mancano dalla frase (decennio, paese, genere, ambientazione), esclusi i segnali sulla forma della risposta (voti, recensioni). Prima la frase semantica perdeva vincoli (caso 20: "1950s"). A/B controllato (stesso pool, 36 chiamate Cohere): violazioni verificabili 20 con la query italiana, 21 con la sola semantica, 16 con la query composta, mai peggiore della migliore in 12 confronti. Il parser dei segnali deve conservare paese, decennio, generi e ambientazione e descrivere i temi di un film citato come riferimento invece di scrivere "simile a X". `QuerySignals.excluded_genres` ("senza fantascienza") esclude i chunk sui metadati `genres` (parole intere); `hard_exclusions` filtra solo i titoli. `constraints.constraint_report` calcola (nello step `rerank` del trace, chiave `constraints.checks`) uno stato per vincolo e per film: `verified` (metadati: generi, anno/decennio), `probable` (tutti i termini chiave nella trama), `not_verifiable` (finali, tono, emozioni, termini assenti: l'assenza non prova nulla), `contradicted` (metadati o frase esplicita nella trama); un requisito negato ("non-tragic ending") non è mai `probable` e nessun segnale debole scarta un film; un segnale positivo che ripete un genere richiesto non riceve un secondo stato. La nazionalità ("Japanese") è origine produttiva, non trama: `verified` solo se i generi del catalogo la nominano ("Japanese Movies"), altrimenti `not_verifiable` (un personaggio giapponese non basta). Al prompt arriva `metadata.constraints_summary` (`constraint_summary`): una riga per film e vincolo con cosa si può affermare; il report completo resta nel trace. `tests/answer_checks.py` controlla una risposta finale contro gli stati (usato da `tests/test_answer_constraints.py` su risposte reali registrate e dagli script di valutazione e2e). `hard_exclusions` diventano controlli `title_exclusion` su titolo e cast. Lo step `rerank` riporta `rerank_query` e `constraints`. Dopo Cohere/LLM `_rerank(..., signals=)` chiama `constraints.demote_contradicted`: riordino stabile che mette dopo i film contraddetti dai soli metadati (genere, genere escluso, decennio, titolo escluso), senza scartarli né usare trama o tono. A/B reale del 2026-10-26 (5 casi, stesso pool di 10, 15 chiamate Cohere): violazioni nei top 3 4→3 con ciascuna delle tre query; il caso 20 resta (nessun candidato conforme nel pool), campione piccolo e metrica identica al criterio del riordino.

- **Limiti per turno** (`orchestrator._Limits`, `CONFIG["orchestrator"]`): oltre a `max_tool_calls_per_turn`, `max_iterations` (12: chiamate del planner), `max_execution_time` (180 s dall'inizio di `run`) e `token_budget` (200.000: `usage.total_tokens` delle chiamate del planner, 0 se la risposta non lo riporta) sono vincolanti e controllati prima di ogni nuova pianificazione; raggiunto uno, il ciclo si ferma (`stop_reason` e fallback `max_iterations`/`max_execution_time`/`token_budget`, raccontati dalla storia) e si risponde con ciò che c'è. Valori larghi per scelta (portfolio, pochi utenti); non interrompono un tool in corso né limitano la risposta finale. Test in `tests/test_orchestrator.py`.
- **Ciclo multi-tool** (`LLMOrchestrator.run`): la regola "un solo tool per turno" non esiste più. Il primo `_plan_first` (la stessa chiamata di prima, `_plan_turn` ne è il wrapper a tupla usato dal routing eval) sceglie il primo tool ed elenca le `parts` della richiesta (`{part, tool}`; voci con tool sconosciuto scartate); serve un altro passo se `more_steps` è true **o** una parte ha un altro tool. Solo allora `_plan_next` fa una chiamata in più, con i risultati già ottenuti (riassunto fino a `STEP_SUMMARY_CHARS`) e le parti ancora senza tool eseguito, e ritorna il passo successivo o `{"done": true}`. Un turno a un solo tool costa quindi le stesse chiamate LLM di prima. Il ciclo finisce con `complete` (nessuna parte pendente), `done`, `repeated_step`, `unknown_tool_or_low_confidence`, `planner_failed`, `required_tools`, `max_tool_calls` (motivo in `decision["planning"]["stop_reason"]`); prima era: `done`, passo ripetuto (stesso tool e argomenti), passo sconosciuto o con `confidence` sotto soglia, errore del planner (mai un fallback a `rag_search` dopo il primo passo: si risponde con ciò che c'è), `required_tools` (un solo passo) o `CONFIG["orchestrator"]["max_tool_calls_per_turn"]` (10). Il chiarimento è solo al primo passo. Le parti pendenti a fine turno arrivano alla risposta finale come "Parti della richiesta NON eseguite" (da dichiarare "non cercate", mai "non trovate"; caso reale 2026-10-24: intervista mai cercata e riportata come non trovata) e lo step `planning` (`STEP_PLANNING`, solo se i tool sono più di uno, resta una parte pendente o c'è un fallback) le racconta all'utente nella storia ("Non ho cercato: …"). La risposta finale riceve tutti i risultati (`tool_results`, un blocco per tool) e le `tool_final_instructions` di ogni tool usato. `decision` ha `tool` e `result` del primo passo, più `tools` e `calls` (`{tool, arguments, result}`); l'orchestratore emette per ogni chiamata, mentre accade, `tool_selection` (prima del tool), `tool_outcome` (dopo) e la trace del tool (vedi "Avanzamento in tempo reale"), `TurnResult.tools` elenca i tool: i presenter mostrano solo i tool eseguiti (nessun output RAG se il RAG non è stato chiamato). I limiti per turno (`tmdb.max_calls_per_turn`, `you_tube.max_searches_per_turn`) contano sul `turn_id`, non sulla run. Errori del tool DB: `metadata.error_kind` `unsupported_request` (nulla nella whitelist, es. filtro per attore) o `parser_failed`, con regola in `final_instructions`.
- **Offerta di altro (`follow_up`)** (`turn.RESULT_FOLLOW_UP`, `orchestrator._follow_up`): un tool può mettere nel risultato (fuori da `metadata`, quindi fuori dal prompt finale) `follow_up = {"available": bool, "reasons": [str], "summary": str}`. Se `available` è vero il ciclo chiama `_plan_next` anche con `more_steps` falso e senza parti pendenti; `_summarize_call` mostra al planner `summary` al posto di `Metadata` troncato a `STEP_SUMMARY_CHARS`; `_plan_next` aggiunge una riga che dice quali motivi ci sono e chiede se ciò che c'è basta (altrimenti il passo successivo, altrimenti `done`). La sufficienza la giudica il planner LLM sulla richiesta e su `summary` (outline, cosa è stato letto e cosa no), non una soglia del tool. Chi non produce `follow_up` costa le stesse chiamate di prima (`tests/test_orchestrator_follow_up.py`, parametrizzato). Freni: `done`, `repeated_step` (stessi tool e argomenti), `max_tool_calls_per_turn`, e il tool smette di offrire quando non ha più budget (chiamate o contesto) o dopo `rate_limited`. Lo usano `wikipedia_search` e `tmdb_search`: quest'ultimo lo offre (motivi `not_found`, `unverified_match`, `empty`; riassunto con le richieste non risolte) quando una richiesta non trova nulla, così il planner può passare a un altro tool invece di chiudere sul fallimento (errori di limite, chiave o rete non si offrono); i risultati riusciti non hanno la chiave. **Fine del ciclo** (`_plan_next`, contratto in `orchestrator.NEXT_STEP_FORMAT`, aggiunto alle istruzioni di quella sola chiamata; classificazione pura `_classify_next_step`): conclusione esplicita = `{"done": true}` (booleano vero) oppure un segnale di stop **definito dal contratto** (`tool_name` nullo, vuoto o `done`/`none`/`stop`) non contraddetto da `done: false` né da `more_steps: true`; in tal caso `stop_reason = "done"`, nessun fallback e nessun avviso. Risposta **incompleta o contraddittoria** (`{}`, solo `confidence`, `done: false` senza tool, `done` stringa o numero, `tool_name` nullo con `more_steps: true`, `tool_name` non stringa) = `stop_reason = "planner_incomplete"` con l'avviso `next_step_failed`. Restano errori con avviso: testo non JSON o non oggetto (`planner_failed`), tool nominato ma non ammesso o confidenza sotto soglia (`unknown_tool_or_low_confidence`). `decision["planning"]["planner_output"]` (e lo step `planning`) registra cosa ha risposto il planner **senza testo libero né argomenti** (`_planner_detail`: nomi delle sole chiavi note, altre come `<key>`; `done`/`confidence`/`more_steps` scalari, stringhe come `<str>`; `tool_name` solo se è un tool dell'app o una parola di stop). - **Regole di routing** (`CONFIG["orchestrator"]["instructions"]`, in ordine di priorità): 0) **chiarimento**: se l'utente chiede di un film o una serie precisi ma né la richiesta né la history bastano a identificarli (es. La regola 2 dichiara che MovieLens non ha attori, registi, cast né giudizi della critica; i film di una persona e i giudizi della critica vanno a `tmdb_search` (`discover_movies` con `people`, `max_rating`, `sort: rating_asc`/`rating_desc`); `rag_search` non si usa per filmografie, voti o giudizi né come ripiego. - **Completamento RAG → TMDb** (`tool/tmdb/enrich.py`, `CONFIG["orchestrator"]["rag_enrichment"]`): dopo `rag_search` l'orchestratore passa il risultato a `TmdbRagEnricher`, che prende i chunk finali (dopo il rerank, al massimo `max_candidates`, nell'ordine del RAG, senza duplicati), cerca ciascun titolo in `en-US` senza filtro d'anno (`ctx.year_after_search`: il filtro di TMDb è esatto e l'anno del corpus spesso sbagliato di 1, la ricerca ripetuta faceva saltare il terzo candidato con `max_calls_per_turn` 6; `_pick_work` controlla l'anno ±1 sui risultati, la ricerca con filtro è il ripiego se nessun risultato è compatibile) (i titoli del corpus sono inglesi) e aggiunge in `metadata.tmdb_enrichment` i metadati solo se il titolo coincide con titolo o titolo originale TMDb (maiuscole, spazi e punteggiatura ignorati; **mai** per inclusione: "The Sinner" non è "The Sinners") e un anno RAG noto è confermato da un anno TMDb entro ±1; il lookup usa `ctx.strict_identity`, quindi più risultati ugualmente validi danno `ambiguous`.   - **Dato e scopo**: due funzioni e basta. (1) `operation: resolve`: distingue le opere con lo stesso titolo con anno, regista e ID IMDb e TMDb. (2) `operation: relations`: identifica l'opera e legge le relazioni **dichiarate** su Wikidata: opere da cui è tratta (fonte letteraria o film d'origine, `P144`/`P4969`), opere basate su di essa (remake, adattamenti, opere ispirate, stesse proprietà in senso inverso), precedente e successiva nella serie (`P155`/`P156`), altre opere del franchise o della serie (`P8345`/`P179`). Il budget è del turno (`turn_id`), come OMDb e TVmaze. Nessuna chiave; User-Agent descrittivo (policy Wikimedia); timeout 15 s (il Query Service interrompe le query oltre circa un minuto: viste in valutazione una da 51 s e una in 504 dopo 65 s, entrambe scritte male); nessun retry; su HTTP 429 una pausa in memoria condivisa dal processo (`Retry-After` se presente, tra 1 e 60 s, altrimenti 5 s; l'header su questo servizio non è stato osservato).

Nel testo SPARQL entrano soltanto id che passano un controllo rigido (`Q` + cifre, `tt` + 7–9 cifre, un intero TMDb, un codice lingua di 2–3 lettere) e il titolo dell'utente solo dentro UN letterale stringa con backslash e virgolette protetti e caratteri di controllo tolti (`sparql_literal`, usato da `label_request`), che non si può chiudere dall'interno; negli altri casi il titolo è solo il parametro `search` della ricerca di entità; ogni query è legata a entità date (o a un ID esterno esatto) e ha `LIMIT 500`. Con un ID IMDb o TMDb l'ID è l'identità (il TMDb richiede `type`: gli ID di film e serie si sovrappongono). **Omonimi (correzione del 2026-10-29, trovata dallo smoke test live)**: la ricerca di entità ordina per notorietà e mescola ogni tipo di elemento, trova anche per prefisso («Crash» porta «Crash Bandicoot») e con 10 risultati il film *Crash* del 1996 era al 21° posto su 50: il tool vedeva solo quello del 2004 e lo dava per certo.
