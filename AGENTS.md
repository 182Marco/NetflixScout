## 1. Contesto del Progetto

**Scopo**: assistente conversazionale da terminale che consiglia film usando RAG sul CMU Movie Summary Corpus, un DB SQL locale read-only di MovieLens 32M (voti, classifiche, generi per anno, tag), l'API TMDb (dati aggiornati: cast, uscite, streaming, serie, persone, trending) e la YouTube Data API v3 (video su un film identificato: interviste a regista e cast, making-of, dietro le quinte, commenti degli autori). Risponde solo a domande cinematografiche (classificatore anti off-topic e anti jailbreak).

**Stack**
- Python 3.11 (`.venv/` locale), nessun `pyproject.toml`: le dipendenze stanno in `requirements.txt` (versioni pinnate).
- LLM ed embedding: `openai` (Responses API + Chat Completions per il classificatore), `sentence-transformers`/`torch` per gli embedding locali.
- Vector store: `chromadb` persistente in `dbVettoriale/<backend>/` (`openai` | `local`), similarità cosine.
- Retrieval: semantico, BM25 (`rank-bm25`), ibrido con RRF.
- DB MovieLens: `sqlite3` della stdlib; CSV e DB in `movie_db/data/` (ignorata da git, read-only a runtime).
- Rerank: `cohere` (`rerank-v3.5`) oppure LLM.
- TMDb: `urllib.request` della stdlib (nessuna dipendenza nuova), chiave da `.env` (`VUE_APP_TMDB_API_KEY`, `VUE_APP_TMDB_BASE_URL`).
- YouTube: `urllib.request` e `zoneinfo` della stdlib (nessuna dipendenza nuova, nessun MCP: tool in-process), chiave `YOUTUBE_API_KEY` da `.env`, letta solo da `youtube/auth.py`.
- Modelli dati: `pydantic` v2. Loader: `pypdf`, `python-docx`, `beautifulsoup4`, `markdown-it-py`.
- Test: `pytest`. Nessun linter o formatter configurato.

**Flusso a runtime** (`app.py`)
```
input + ultimi classifier_context_messages della history → classify_query_domain (gpt-4o-mini, JSON) ──non cinema──→ messaggio di blocco it/en
                         │ cinema
                         ▼
LLMOrchestrator (orchestrator.py) → sceglie il tool → RagTool.run → run_rag (retrieve + rerank, nessuna generazione) → TmdbRagEnricher (metadati TMDb dei candidati)
                                                   oppure MovieDbTool.run → parser LLM → MovieDbQuery → SQL whitelistato read-only
                                                   oppure TmdbTool.run → TmdbToolInput validato → risoluzione ID → endpoint fissi (budget per turno) → contesto limitato
                                                   oppure YoutubeTool.run → YoutubeToolInput validato → search.list per categoria (limite per turno) → un videos.list → filtro di pertinenza → metadata + trace
                         ▼
il planner può concatenare altri tool nello stesso turno (fino a max_tool_calls_per_turn, ogni passo usa i dati dei precedenti) → l'orchestratore genera la risposta finale (final_instructions + tool_final_instructions di ogni tool usato) → history → compattazione oltre memory_window_size

Ogni step (query riscritta, tool scelto, esito e secondi, trace del tool, fallback) va al TurnObserver del canale MENTRE accade; il terminale lo stampa subito (storia in poche frasi + blocco del tool), il web riceve gli stessi dati in JSON. Alla fine present(..., streamed=True) aggiunge solo la risposta.
```

## 3. Linee Guida di Stile e Architettura

**Formattazione**
- PEP 8, indentazione di 4 spazi, righe di circa 100 caratteri, virgole finali nelle chiamate su più righe.
- `from __future__ import annotations` in testa ai moduli nuovi; type hint moderni (`list[dict]`, `str | None`).
- Import relativi dentro `rag/FromQueryEmbeddingToRes/` (`from .models import ...`), assoluti dalla root (`from rag.FromQueryEmbeddingToRes... import ...`).
- Le funzioni private del modulo hanno il prefisso `_`; argomenti keyword-only (`*`) per le API pubbliche (`run_rag`, `Tool.run`).
- Naming misto italiano/inglese **già esistente** (`recupera`, `genera`, `apri_collection`, `indicizza`, `testo`, `k_largo`, `k_finale`): rispetta il nome già usato nel modulo che tocchi, non rinominare.
- Prompt e messaggi per l'utente finale in italiano, docstring ed errori tecnici in inglese.

**Pattern architetturali**
- **Parametri RAG scelti dal planner**: solo `k_finale` (quanti film chiede l'utente; null = default di `CONFIG["rag"]["retrieval"]`, con `limits.k_finale` min/max). `RagToolInput` lo espone (`extra="forbid"`); `RagTool.run` lo passa a `retrieval_params.resolve_retrieval`, che lo clampa, tiene `k_finale <= k_largo <= fetch_k`, ignora valori non validi e ogni altra chiave, e lavora su una copia della config. Lo step `retrieval` riporta `retrieval_params` (`effective`, `overridden`). `search_mode`, `k_largo`, `fetch_k` e `genre_boost` sono stati provati nello schema del planner e **rimossi**: due A/B live del 2026-10-24 (10 domande, default contro planner) non hanno mostrato alcun beneficio oltre al conteggio (nei casi in cui differivano solo quelli, 3 su 3 uguali; commedie giapponesi anni 50: più violazioni dei vincoli per film; il planner scriveva `genre_boost` anche fuori scala, 1,5–2,0). Il guadagno netto è `k_finale` uguale al numero chiesto (7 migliori, 0 peggiori, 3 uguali nel secondo run; limite: la metrica premia il conteggio corretto, quindi è una prova sul numero di film, non sulla qualità dei titoli). `search_mode` bm25/hybrid non è stato mai scelto dal planner nel secondo run, quindi la sua utilità resta non dimostrata. Valutazione: `routing_cases.py` (`expected_rag`) e `python -m movie_db.harness.evaluation.run_rag_params_eval --live` (A/B, ~10 planner + 20 parser + 20 Cohere, pause di 7 s). Correzione collaterale: `bm25`/`hybrid` leggono la collection a pagine e tengono l'indice in cache (`hybrid.py`; prima `collection.get()` falliva con "too many SQL variables" su 42k chunk).
- **Config-driven**: tutti i parametri (modelli, k, backend, prompt) vivono in `CONFIG` in `app.py`. Niente valori hardcoded nei moduli: passa `config` come dict. Gli override passano da `build_runtime_config(overrides)`.
- `_resolve_runtime_config` normalizza la config RAG (backend effettivo, `db_dir`, default della conversazione): chiamala prima di accedere a vectorstore ed embedding.
- **Contratto dei tool**: ogni tool rispetta il `Tool` Protocol (`name`, `description`, `input_schema`, `run(*, query, params, conversation_history) -> dict`). `input_schema` deriva da un modello Pydantic (`model_json_schema()`). Un nuovo tool si registra in `build_app` e in `CONFIG["orchestrator"]["allowed_tools"]`, senza toccare il core.
- **Separazione dei ruoli**: `RagTool`/`run_rag` restituiscono solo evidenza strutturata (`chunks` + `metadata` + `trace`); la risposta finale la genera solo l'orchestratore.
- **Avanzamento in tempo reale**: il turno è sincrono, quindi senza osservatore l'utente non vede nulla finché `LLMOrchestrator.run` non ritorna (era la causa del terminale muto). `handle_query(..., observer=)` e `run(..., observer=)` accettano un `TurnObserver` (`turn.py`: `step(TraceStep)` e `status(stage)`): l'orchestratore emette gli step **mentre accadono** (`query_rewrite`, per ogni tool `tool_selection` con `purpose` e `arguments` **prima** della chiamata, poi `tool_outcome` con `elapsed_ms`/`status`/`reason` e la trace del tool, `planning` per ultimo) e `status(answering)` prima della risposta finale; un osservatore che solleva non rompe il turno. `TurnResult.steps` e `TurnResult.story` sono gli stessi che vede l'osservatore (`_TurnRecorder` in `app.py`); un orchestratore finto nei test deve emettere gli step (`tests/turn_support.py:stream_decision`). Ogni tool mette in `result["outcome"]` (`turn.tool_outcome`: `ok|empty|error` + `reason`, fuori da `metadata`) l'esito che la storia racconta; senza `outcome` conta la presenza di `chunks`. I fallback silenziosi (`planner_failed`, `low_confidence`, `unknown_tool`, `next_step_failed`, `max_tool_calls`, `answer_failed`) stanno in `decision["planning"]["fallbacks"]` e la storia li dice solo quando accadono.
- **Terminale e web uniformi**: stesso contenuto, formato diverso. Ogni step ha una vista in `presenters/*_view.py` (testi it/en, dati) e i due canali ne cambiano solo la forma; la storia (`story_view.StoryBuilder`) è un'unica sequenza di `StoryLine(level, text, tool)` (il terminale aggiunge l'emoji per `level`, il web lascia l'icona al frontend; dopo `MAX_OK_LINES` esiti positivi restano solo i problemi). Gli step di flusso (`classification`, `query_rewrite`, `tool_selection`, `tool_outcome`, `planning`) sono raccontati dalla storia e non hanno renderer né serializer; ogni altro kind deve stare sia in `STEP_RENDERERS` sia in `STEP_SERIALIZERS` (`tests/test_presenter_parity.py`). Un nuovo tool aggiunge la vista condivisa, il renderer terminale e il serializer web.
- **Il nucleo non stampa**: `handle_query` produce un `TurnResult` con gli step (`trace` dei tool inclusa). L'output sta solo in `presenters/<canale>/<tool>/` (`rag`, `db`, `api`); fuori dalle cartelle dei tool solo il collante del flusso e le viste condivise; un nuovo tool aggiunge `presenters/terminal/<tool>/` e `presenters/web/<tool>/` (struttura verificata da `tests/test_tmdb_presenters.py`). Il canale (`OutputChannel`) lo dichiara l'entry point: `python app.py` → `terminal`, la futura route FastAPI → `web`. Niente `print` fuori da `presenters/terminal/` (eccezioni: builder offline, loop legacy in `chat.py`).
- **Query autonoma per i follow-up**: nella stessa chiamata LLM con cui sceglie il tool, l'orchestratore (`_plan_turn`) riscrive la domanda in modo autonomo usando la history (`standalone_query`) e la passa a **qualunque** tool, anche con `required_tools` o fallback. Senza history o se l'LLM fallisce si usa la domanda originale. Per `rag_search` la ricerca parte sempre dalla `standalone_query` (le parole dell'utente); `arguments.query` del planner arriva al parser dei segnali solo come `query_hint` ("Planner rewrite"), perché può essere vaga (caso reale: "Film simili a Mare dentro, che affrontino temi e atmosfere analoghi"); il trace `retrieval` riporta entrambe. La history va passata **intera e invariata** (niente finestre scorrevoli): un prefisso stabile permette al prompt caching del provider di riusarla.
- **Contesto del classificatore**: `handle_query` passa a `classify_query_domain(query, history)` gli ultimi `CONFIG["orchestrator"]["classifier_context_messages"]` messaggi della history. Il guardrail gira prima della riscrittura `standalone_query`: senza contesto un follow-up come "ne puoi trovare 3 più recenti?" verrebbe bloccato. La history serve solo a risolvere riferimenti impliciti; si classifica sempre l'ultima query. Il prompt considera cinematografiche anche le richieste su un film già citato (trama, dettagli, traduzione) in qualsiasi lingua: chiedere la risposta in un'altra lingua non è un jailbreak (prima "Could you get in english the plot from the movie you just advised?" veniva bloccata). Lo step `classification` resta nel trace ma non viene stampato (né a terminale né sul web): un blocco mostra solo il messaggio di blocco. **Lingua**: la history risolve i riferimenti, non decide la lingua; `detect_language_markers` (parole funzionali it/en) sovrascrive `is_italian` solo con almeno 2 marcatori di una lingua e nessuno dell'altra (prima "Chi l'ha diretto e quanto dura?" dopo un titolo inglese era classificata inglese); altrimenti vale il classificatore.
- **Trace dei tool**: ogni tool restituisce `"trace": [{kind, title, data}]` fuori da `metadata` (che finisce nel prompt). Un `kind` nuovo ha il renderer nella cartella del suo tool (`presenters/terminal/<tool>/renderer.py`, su una vista condivisa) e va registrato in `presenters/terminal/renderer.py:STEP_RENDERERS` (firma `(step, language)`, `language` = `TurnResult.language`) **e** il serializer in `presenters/web/payload.py:STEP_SERIALIZERS`, altrimenti viene stampato col fallback generico.
- **Testo dell'embedding**: il corpus è composto da trame in inglese. Il parser `_extract_query_signals` (`retrieval.py`) produce `QuerySignals` in inglese con `semantic_query` (la frase su cui si fa l'embedding) e `genres` (vocabolario del corpus). `vectorstore.search` fa l'embedding di `semantic_query`, altrimenti della query originale, **mai** del join dei `positive_signals`: un insieme di keyword italiane faceva finire il retrieval su film italiani o storici. Il genere non viene indicizzato nel testo: entra nel ranking con il boost `retrieval.genre_boost` sul pool di `retrieval.fetch_k` e nel documento passato al reranker (`rerank._documento_per_rerank`). Lo step `retrieval` del trace riporta `embedded_text` e `signals`. Il reranker riceve `compose_rerank_query`: `semantic_query` (altrimenti la query) più "Must match: …" con i segnali positivi e i generi richiesti le cui parole chiave mancano dalla frase (decennio, paese, genere, ambientazione), esclusi i segnali sulla forma della risposta (voti, recensioni). Prima la frase semantica perdeva vincoli (caso 20: "1950s"). A/B controllato (stesso pool, 36 chiamate Cohere): violazioni verificabili 20 con la query italiana, 21 con la sola semantica, 16 con la query composta, mai peggiore della migliore in 12 confronti. Il parser dei segnali deve conservare paese, decennio, generi e ambientazione e descrivere i temi di un film citato come riferimento invece di scrivere "simile a X". `QuerySignals.excluded_genres` ("senza fantascienza") esclude i chunk sui metadati `genres` (parole intere); `hard_exclusions` filtra solo i titoli. `constraints.constraint_report` calcola (nello step `rerank` del trace, chiave `constraints.checks`) uno stato per vincolo e per film: `verified` (metadati: generi, anno/decennio), `probable` (tutti i termini chiave nella trama), `not_verifiable` (finali, tono, emozioni, termini assenti: l'assenza non prova nulla), `contradicted` (metadati o frase esplicita nella trama); un requisito negato ("non-tragic ending") non è mai `probable` e nessun segnale debole scarta un film; un segnale positivo che ripete un genere richiesto non riceve un secondo stato. La nazionalità ("Japanese") è origine produttiva, non trama: `verified` solo se i generi del catalogo la nominano ("Japanese Movies"), altrimenti `not_verifiable` (un personaggio giapponese non basta). Al prompt arriva `metadata.constraints_summary` (`constraint_summary`): una riga per film e vincolo con cosa si può affermare; il report completo resta nel trace. `tests/answer_checks.py` controlla una risposta finale contro gli stati (usato da `tests/test_answer_constraints.py` su risposte reali registrate e dagli script di valutazione e2e). `hard_exclusions` diventano controlli `title_exclusion` su titolo e cast. Lo step `rerank` riporta `rerank_query` e `constraints`.

Il primo `_plan_first` (la stessa chiamata di prima, `_plan_turn` ne è il wrapper a tupla usato dal routing eval) sceglie il primo tool ed elenca le `parts` della richiesta (`{part, tool}`; voci con tool sconosciuto scartate); serve un altro passo se `more_steps` è true **o** una parte ha un altro tool. Solo allora `_plan_next` fa una chiamata in più, con i risultati già ottenuti (riassunto fino a `STEP_SUMMARY_CHARS`) e le parti ancora senza tool eseguito, e ritorna il passo successivo o `{"done": true}`. Un turno a un solo tool costa quindi le stesse chiamate LLM di prima. Il ciclo finisce con `complete` (nessuna parte pendente), `done`, `repeated_step`, `unknown_tool_or_low_confidence`, `planner_failed`, `required_tools`, `max_tool_calls` (motivo in `decision["planning"]["stop_reason"]`); prima era: `done`, passo ripetuto (stesso tool e argomenti), passo sconosciuto o con `confidence` sotto soglia, errore del planner (mai un fallback a `rag_search` dopo il primo passo: si risponde con ciò che c'è), `required_tools` (un solo passo) o `CONFIG["orchestrator"]["max_tool_calls_per_turn"]` (10). Il chiarimento è solo al primo passo. Le parti pendenti a fine turno arrivano alla risposta finale come "Parti della richiesta NON eseguite" (da dichiarare "non cercate", mai "non trovate"; caso reale 2026-10-24: intervista mai cercata e riportata come non trovata) e lo step `planning` (`STEP_PLANNING`, solo se i tool sono più di uno, resta una parte pendente o c'è un fallback) le racconta all'utente nella storia ("Non ho cercato: …").
